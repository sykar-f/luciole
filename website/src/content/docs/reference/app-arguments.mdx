An app that takes command-line options declares them in `app/args.ts` (optional), with
`defineArgs` from `airtty/args` and a zod 4 schema, or any Standard Schema that also
implements Standard JSON Schema. The framework parses them the same way everywhere,
generates `--help`, and hands them to the Server, which reads them typed.

## Grammar

The grammar comes from the options' JSON Schema; a camelCase property becomes `--kebab-case`.

| Schema               | Command line                                                    |
| -------------------- | --------------------------------------------------------------- |
| boolean              | `--flag`, `--no-flag`                                           |
| string, enum, number | `--flag v`, `--flag=v` (numbers converted before validation)    |
| `true \| string`     | `--flag` alone, or `--flag v` if the next word is not an option |
| array of scalars     | repeatable: `--flag a --flag b`                                 |

`.meta()` adds `short` (one letter; `-abc` groups booleans), `placeholder`, `description`,
`kind: "path"` (resolved against the directory the command was typed in) and `env` (a
variable read when the option is absent: command line, then variable, then default). A
nested object or another kind of union is refused at build time. A usage error names the
option, suggests the closest one ("did you mean") and exits with code 2. `--help` lists the
app's options, then the runtime's, then the examples.

The runtime's options are reserved: the build refuses an app that declares `--url`, `--on`,
`--target`, `--grace`, `--yes`, `--help`, `-h`, `--version` or `--new`.

## Reading them on the Server

The value is typed by the import, with no code generation:

```ts
import "server-only";
import cli from "../app/args";
export const config = cli.get(); // { harness?: "claude" | "codex"; mode: "read" | "ask"; … }
```

`getArgs()` from `airtty/server` returns the same value, untyped, and `getLaunch()` the
launch: `{ scope, id?, cwd }`. The Server is the authority: it parses the line it receives
again before serving, and a refused line stops it (code 2, the message in its log).

**One Server, one set of arguments**: `get()` is a constant of the process, safe at module
level, in a singleton or under `"use cache"`. There is no Client API: `get()` throws in the
Client, and the page passes the UI what it needs as props. `app/args.ts` runs in the
launcher, the binary and the Server, so it may import neither `server-only`, `client-only`,
`server/` nor OpenTUI.

## How each entry point passes them

Every entry point that starts a Server accepts the options, checks them before starting it,
and passes them in the `AIRTTY_ARGS` variable, never on its command line, which `ps` shows
to other users.

| Entry point                                       | The app's options                                                              |
| ------------------------------------------------- | ------------------------------------------------------------------------------ |
| `airtty dev --app d -- <options>`                 | after `--`; checked again at every rebuild                                     |
| `airtty ./app <options>`, a git source            | everything that is not `--url`, `--grace`, `--yes`, `-h`                       |
| a binary: `app <options>`                         | everything that is not a runtime option                                        |
| `app serve [--http … \| --socket …] -- <options>` | after `--`                                                                     |
| `app --on host <options>`                         | sent on the standard input of the remote `serve --detach`; paths resolve there |
| `airtty start --role server -- <options>`         | after `--`                                                                     |
| `--url`, `airtty connect`, the generic Client     | refused: this Client joins a Server that already runs                          |

The build bundles `app/args.ts` into `.airtty/args/` and writes its JSON Schema into
`.airtty/metadata.json` (`args`), which a host reads without running the app.

<Note>
  Two launches with different arguments never share a Server: the arguments' fingerprint is part of
  the key that decides which Server a launch joins, and of every `"use cache"` key. In the browser
  (`--web-local`), the Server has no command line and takes the schema's defaults.
</Note>
