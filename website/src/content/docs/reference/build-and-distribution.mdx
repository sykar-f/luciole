This page lists what `luciole build` writes, the options it takes, and how a build becomes a
binary, an npm package or a Server on another machine. Run every command from the app's
directory, or pass `--app <dir>`: the output is then `<dir>/.luciole/`.

## What `luciole build` writes

Three more entries appear when the build needs them:

- `args/`: `app/args.ts`, bundled for the launcher and the binary, when the app has arguments.
- `web/`: the web runtime and its page, with `--web` or `--web-local`.
- `web-server/`: the Server's code for a browser Worker, with `--web-local`.

What each bundle holds:

- The Client bundle holds the runtime that draws in a terminal window, and this app's Client
  Components.
- The Client bundle holds no Server code. It has no Server page, no Server Function's code, no
  `server-only` module and nothing under a `server/` directory.
- Business rules written in Client Components, such as when to retry a save, are in the Client
  bundle.
- The Server bundle holds the HTTP runtime, routes, Server Functions and business code. It does
  not import OpenTUI.
- Each bundle has a linked source map. Bun applies it to stack traces at run time, in
  development and in production.

`.luciole/client` and `.luciole/server` are not a delivery format. They carry no manifest or
lockfile to install elsewhere. Give a machine of known platform a
[compiled binary](#compile-a-single-binary). On an unknown one, open the app from its source
(`luciole git+…`), which installs it from its `bun.lock` and builds it there.

## Which options `luciole build` takes

| Option                             | What it does                                                                   | Default                           |
| ---------------------------------- | ------------------------------------------------------------------------------ | --------------------------------- |
| `--app <dir>`                      | builds the app in `<dir>`, into `<dir>/.luciole/`                              | `.`                               |
| `--app-bundle`                     | fails the build when `.luciole/app/` cannot be written                         | the build warns and goes on       |
| `--sign-bundle`                    | signs `app/manifest.json` with your publisher key, and implies `--app-bundle`  | unsigned                          |
| `--web`                            | adds the web runtime in `.luciole/web/`, and implies `--app-bundle`            | no web build                      |
| `--web-local`                      | writes a static site where the Server runs in the browser, and implies `--web` | no web build                      |
| `--compile`                        | writes a [single binary](#compile-a-single-binary)                             | no binary                         |
| `--name <name>`                    | names the binary and the app                                                   | the app directory's name          |
| `--client-only`                    | leaves the Server out of the binary                                            | Client and Server                 |
| `--target <target>`                | builds for [another platform](#build-for-another-platform)                     | this machine's platform           |
| `--runtime official\|host\|<path>` | chooses the [Bun runtime](#choose-the-bun-runtime-the-binary-embeds) to embed  | `official`                        |
| `--portable`                       | turns the runtime's portability warning into an error                          | a warning                         |
| `--native-dir <dir>`               | takes [native packages](#ship-native-server-packages) from `<dir>`             | the app's `node_modules`          |
| `--outfile <file>`                 | writes the binary to `<file>`                                                  | `.luciole/bin/<os>-<arch>/<name>` |
| `--sign <identity>`                | [signs the macOS binary](#sign-and-notarize-for-macos), ad hoc with `-`        | the linker's ad hoc signature     |
| `--notarize <profile>`             | sends the signed binary to Apple's notary service                              | not notarized                     |

The options from `--name` to `--notarize` apply only with `--compile`. Without it, the build
refuses them.

Other behaviours:

- `luciole build` without `--compile` or `--web` does not touch the network.
- `.luciole/app/` is written in CommonJS, which cannot express a top-level `await`. When Client
  code uses one, the build succeeds without the app bundle, and says which module.

## What a failed build leaves

A failed build leaves the previous build in `.luciole/`. The build assembles everything in a
temporary directory, then publishes it with one rename:

When the app has not changed since the last build, steps 1 and 2 are a copy of `.luciole/`.
`--web` and `--compile` work on that copy, which is published the same way. A build without
them leaves `.luciole/` as it is.

A build killed between steps 4 and 5 leaves no `.luciole/`, and the previous build in
`.luciole-previous/`. The next build that reaches step 4 moves it back to `.luciole/` first:
it then replaces it, or puts it back if the rename (5) fails.

One case does not follow this sequence: **`--outfile` writes the binary outside
`.luciole/`.** The binary is built beside its destination, and replaces the previous one after
step 6. A failed build leaves the previous binary, but it can have updated the `native/`
directory beside it.

If the last move of an `--outfile` binary fails, `.luciole/` already holds the new build.

A build that does not use `--compile` publishes a `.luciole/` without `bin/`. It removes the
binary a previous `--compile` wrote there.

`tests/build.test.ts` makes a build fail in six ways, then checks that `.luciole/` still holds
the previous build:

- the app does not compile
- a step staged with the build, such as `--web`, fails
- the rename (5) fails
- a previous build was killed between steps 4 and 5
- `--web` or `--compile` fails on an up-to-date build
- `--compile --outfile` fails, which also leaves the previous binary

## How the build ID is made

Both roles must come from the same build. The Client sends its build ID with each request, and
a Server of another build refuses the request before decoding it. `tests/transport.test.tsx`
sends a body the Server cannot decode: with an old build ID, the answer is still a `409`.

The build ID is a hash of what the build reads:

- the app's modules in both graphs, every layout, loading and error screen included
- every `.ts` and `.tsx` source of the framework
- the `bun.lock` of the framework's installation, which the build requires
- the app's `bun.lock`, when it is another file
- the sources of the workspace packages the app links (`workspace:*`, outside any
  `node_modules`), since their changes leave the lock as it is
- the app's `package.json`, its `luciole.json` and its icon

The build takes the nearest `bun.lock` above the framework, and above the app. It never looks
past the git checkout.

The lockfile lists the packages of every platform, unlike `node_modules`. Binaries of each
target of one version therefore keep the same ID.

## Compile a single binary

```sh
luciole build --compile [--name notes] [--target t] [--client-only]
# → .luciole/bin/<os>-<arch>/notes  (+ native/)
# → .luciole/client/notes-<os>-<arch>  with --client-only
```

The binary holds the Bun runtime, OpenTUI's native library and the build ID. By default it
holds the Client **and** the Server, business code included, and the build warns about it every
time.

`--client-only` writes the Client alone. Only the full binary carries its identity, which the
launcher reads without running it. `notes --version` prints that identity.

### Choose the Bun runtime the binary embeds

| `--runtime` | What the binary embeds                                                                         |
| ----------- | ---------------------------------------------------------------------------------------------- |
| `official`  | the official Bun of the target, from npm (`@oven/bun-<os>-<arch>`), at the build's Bun version |
| `host`      | the Bun running the build. It only builds for this machine's platform.                         |
| `<path>`    | the Bun executable at that path                                                                |

The official runtime is downloaded **once** and checked against the registry's published
`integrity` (SHA-512). Later builds reuse it from `$XDG_CACHE_HOME/luciole/runtime/` without
the network. `luciole runtime [--target …]` fills that cache ahead of time. Offline and without
a cache, the build fails and says so.

<Note kind="warning">
  The checksum protects against a truncated or altered download. It does not protect against a
  compromised registry: npm signatures are not checked.
</Note>

On macOS, the build warns when the runtime links libraries outside the system, as a Bun from
Nix or Homebrew does. Such a binary would not start on another Mac. `--portable` turns that
warning into an error.

### Build for another platform

`--target` takes one of these platforms:

- `bun-darwin-arm64`, `bun-darwin-x64`
- `bun-linux-x64`, `bun-linux-arm64`
- `bun-linux-x64-musl`, `bun-linux-arm64-musl`

A target other than this machine's also needs `--native-dir`. OpenTUI ships its native library
in one package per platform, and `bun install` installs only this machine's. Without
`--native-dir`, the build stops and names the missing package.

Install the target's packages in a directory of their own, as the build's message says:

1. Copy the app's `package.json` and `bun.lock` into that directory.
2. Run the install there, with `--os` set to the target's system, `linux` or `darwin`:

   ```sh
   bun install --frozen-lockfile --os=linux --cpu='*'
   ```

   The quotes keep zsh from expanding `*`.

3. Pass that directory to `luciole build` with `--native-dir`.

[Ship a binary](/docs/guides/ship-a-binary/#choose-a-target-for-each-machine) shows these steps
for `bun-linux-x64`.

What each Linux binary needs:

- The glibc binary starts on a minimal Debian.
- The musl binary needs `libstdc++` and `libgcc`, which Bun's musl runtime links. On Alpine,
  run `apk add libstdc++`.
- At launch, Bun extracts OpenTUI's library into `$TMPDIR`, which is `/tmp` by default. If that
  directory is mounted `noexec`, set `TMPDIR` to an executable directory.

`bun run test:linux` runs these variants in containers without Bun. It needs Docker.

### Ship native Server packages

A package with native code, such as sharp, does not fit in a single file: it holds a `.node`
addon and the libraries it links. The build keeps it external on the Server. `--compile` puts
it next to the binary in `native/node_modules/`, with only the target's platform packages.

To build for another platform, install the app's packages for that target **from its
lockfile**, then pass that directory with `--native-dir`:

```sh
bun install --frozen-lockfile --os=linux --cpu=x64
```

`native/` travels with the binary: in the `--on` archive, in the npm platform package, and in
the installation directory.

## Sign and notarize for macOS

Without options, the macOS binary carries the linker's ad hoc signature. It runs on the machine
that built it, or when copied with `scp` or `curl`. Gatekeeper blocks it when a browser
downloaded it.

```sh
# once: App Store Connect credentials in the keychain
xcrun notarytool store-credentials luciole-notary --apple-id … --team-id … --password …
luciole build --compile \
  --sign "Developer ID Application: Example Ltd (TEAMID1234)" --notarize luciole-notary
```

`--sign <identity>` signs with the hardened runtime, a secure timestamp and two entitlements,
then verifies the signature:

- `allow-jit`: without it, Bun stops, and `bun:ffi` refuses to load OpenTUI.
- `disable-library-validation`: OpenTUI's library is extracted at launch, and your team did not
  sign it.

`--sign -` makes the same signature ad hoc, without the timestamp, to test locally.

`--notarize <profile>` requires a Developer ID. It sends the zipped binary to `notarytool` and
waits for the verdict. On refusal, it prints Apple's log.

A bare executable cannot have a ticket stapled, so Gatekeeper checks it online at first launch.
For an offline first launch, ship the binary in a signed, notarized and stapled `.dmg` or
`.pkg`.

These options apply to macOS targets, from macOS.
[Troubleshooting](/docs/reference/troubleshooting/#macos-blocks-a-downloaded-binary) shows what macOS prints when it blocks a binary.

<Note kind="warning">
  Notarization has not been run end to end in this repository, for lack of a Developer ID.
</Note>

## What `--on` does on the remote machine

`notes --on [user@]host[:port]` starts the Server on a remote machine and the Client here
([the task, step by step](/docs/guides/opening-an-app/#start-the-server-on-another-machine)):

1. One master ssh connection authenticates once. The probe, the upload, the Server and the
   tunnel reuse it. `LUCIOLE_SSH` replaces `ssh`.
2. The remote machine reports its OS, architecture and libc. It also reports whether this build
   is installed under `~/.local/share/luciole/apps/<app>/<buildId>/` and matches its
   `SHA256SUMS`.
3. When the build is missing or fails that check, a binary is uploaded:
   - this binary, when the remote machine has its platform
   - otherwise the one `--target` gives, which must be the same app, the same build and the
     remote machine's platform
4. The remote machine checks the archive, then swaps it in whole. It refuses a tampered build,
   and never starts it.
5. `<app> serve --detach` finds the managed Server of this launch, or starts one detached from
   ssh. The app's options reach it on standard input. A command line would show them to other
   users through `ps`.
6. A tunnel `ssh -N -L <local socket>:<remote socket>` joins it to the Client.

When the tunnel drops, the Client relaunches it after 1 s, 2 s, 4 s, up to 30 s, on the same
local socket. A relaunched tunnel runs with `BatchMode`, so it never prompts.

## How long a Server lives

A Server the launcher starts, locally or with `--on`, is detached. It runs in its own process
group, writes to its log, and lives as long as its Clients need it:

| Event                                               | Effect                                                                    |
| --------------------------------------------------- | ------------------------------------------------------------------------- |
| A Client runs                                       | it pings `POST /lifetime/ping` every 10 s, and any request counts too     |
| <kbd>Ctrl+C</kbd> or `app.quit`, to quit on purpose | `POST /lifetime/leave`. When the last Client leaves, the Server stops     |
| No request or ping for 30 s                         | that Client is lost                                                       |
| The Server's standard input ends without a leave    | the launcher's Client is lost, after a crash or a closed terminal window  |
| The last Client is lost                             | the grace period starts: 15 min by default, set with `--grace <duration>` |
| A Client comes back during the grace period         | it is attached again, and the grace period stops                          |
| The grace period ends                               | the Server stops                                                          |

A new launch of the same target finds the Server at its socket and checks it with
`GET /lifetime/status`. With the same build and the same arguments, the launch attaches to it.
Otherwise it stops that Server with `POST /lifetime/stop` and starts a new one.

What survives a lost Client:

- **The framework keeps** the Server and its in-memory data during the grace period. It
  re-establishes the tunnel, and restores the route and the named fields.
- **The app is responsible for** every other in-memory state of the Client. It also decides
  what an operation whose outcome is `unknown` means for its business.

## Publish an app to npm

An app is published the way esbuild is. Each platform gets a package with its binary. A main
package lists them in `optionalDependencies` and in `luciole.binaries`.

```sh
luciole build --compile --name notes --target bun-darwin-arm64
luciole build --compile --name notes --target bun-linux-x64 --native-dir ../notes-linux  # another platform
luciole pack --package @ada/notes --version 1.2.0 .luciole/bin/*/notes
```

`luciole pack` prints the order to publish in, platforms first.

How the launcher installs a published app:

- It only reads the registry, through its public read API: package documents, tarballs and
  search.
- It compares each tarball with its published `integrity`.
- It records what it installed in `$XDG_DATA_HOME/luciole/apps/<app>/`.
- An update writes the new binary next to the old one, switches `installed.json`, then removes
  the old one.
- It refuses a binary whose identity does not match its `package.json`.

## What the build and the launcher do not do yet

- `--on` does not clean up old builds on the remote machine.
- The relaunched tunnel never prompts, so a password-only login does not come back by itself.
- A private npm registry, with a token, is not supported.
- `update` does not apply to git sources.
- `install` does not detect musl. On Alpine it would pick the glibc binary.
- A compiled binary does not embed `.luciole/app/`, so it cannot be opened by URL.
- A compiled Client is rebuilt from `index.js` without its source map. Its stack traces stay in
  the bundle's coordinates.
