This page says which version is current, what a release may change in your app, and how to
move an app to a new one.

## Version

The current release is **{version}**, published on npm under the dist-tag <code>{distTag}</code>.

Five packages share that one version, so an app never mixes two releases:

- `luciole.sh`, the install name: <code>{commands.fromNpm} init my-app</code> creates an app
- `@luciole-sh/core`, the framework and the `luciole` command
- `@luciole-sh/create`, the scaffolder `init` runs
- `@luciole-sh/flow-graph`
- `@luciole-sh/markdown-editor`

A tag with a suffix, such as `v1.0.0-rc.1`, is a preview. It is published under `next`, so
`latest` never points to it.

<Note title="Where this number comes from">
  The build reads the version and the tag from `packages/core/package.json`. A release changes the
  page without anyone editing it.
</Note>

| System  | Status       |
| ------- | ------------ |
| macOS   | Tested in CI |
| Linux   | Tested in CI |
| Windows | Not tested   |

luciole needs Bun <code>{bun}</code>, as the `engines` field says. CI runs the version pinned in `.bun-version`.

The [project status](/status/) lists what is tested and what is not.

## Stability

luciole is at 0.x: it is experimental, and the API is not frozen.

| Release           | Example       | May it break your app?                |
| ----------------- | ------------- | ------------------------------------- |
| Patch             | 0.1.0 → 0.1.1 | No. It keeps the API.                 |
| Minor, before 1.0 | 0.1.x → 0.2.0 | Yes. The CHANGELOG says how to adapt. |

Each break is listed in the CHANGELOG, under **Changed** or **Removed**, and marked
**Breaking**. Nothing else is promised before 1.0.

## Upgrade an app

Upgrade from the app's directory.

1. Update the two packages together:

   ```sh
   bun update @luciole-sh/core luciole.sh
   ```

2. Read the [CHANGELOG](https://github.com/sykar-f/luciole/blob/main/CHANGELOG.md) for every
   release between your version and the new one. Look for the entries marked **Breaking**,
   and apply what each one asks.

3. Check the app. In a starter, `bun run verify` runs the type check, lint, format check and
   build:

   ```sh
   bun run verify
   ```

   If your app has its own checks, run those too.

A patch needs steps 1 and 3. For a minor, do step 2 before step 3.

<Note kind="warning">
  Upgrade `@luciole-sh/core` and `luciole.sh` to the same version. `luciole.sh` depends on
  `@luciole-sh/core`, and a mismatch can leave the `luciole` command on a different release than
  your app's framework.
</Note>

## Changelog

[CHANGELOG.md](https://github.com/sykar-f/luciole/blob/main/CHANGELOG.md) lists every release,
newest first, under **Added**, **Changed**, **Removed** and **Fixed**. Its **Unreleased**
section holds what `main` has and no release has yet.

## Support

Ask a question or report a bug in
[GitHub issues](https://github.com/sykar-f/luciole/issues). Give the version of
`@luciole-sh/core` and the smallest app that shows the problem.

## Security

Do not report a vulnerability in a public issue. Use the
[private advisory form](https://github.com/sykar-f/luciole/security/advisories/new), as
[SECURITY.md](https://github.com/sykar-f/luciole/blob/main/SECURITY.md) explains.

Only the latest release gets security fixes. A fix ships as a patch release of all five
packages.
