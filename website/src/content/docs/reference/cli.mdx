This page lists every `luciole` subcommand and its flags. `@luciole-sh/core` declares two commands: `luciole` and `luciolex`. The install package,
`luciole.sh`, declares only `luciole`: <code>{commands.fromNpm}</code> runs it without installing
it. In a clone of the repository, <code>{commands.fromClone}</code> runs the same CLI from its
sources. An app made by `init` calls the installed `luciole` from its scripts.

```text
luciole <subcommand> [options] [-- app arguments]
luciole <target> [options]      launch an app (path, installed app, npm spec, git source, URL)
luciole                         open the launcher
```

A first argument that is no subcommand and does not start with `-` is a target to launch.

Every subcommand reads its flags by the same rules:

- The CLI's own flags come before `--`. What follows `--` belongs to the app
  ([app arguments](/docs/reference/app-arguments/)), even a word that looks like a CLI flag.
- `--app dir` names the app for `dev`, `build`, `start` and `connect`. Without it, they work
  on the current directory.
- A flag that needs a value and gets none is refused, naming the flag: `luciole build --app`
  prints `--app needs a value`.
- A usage error exits with code 2, any other error with 1.

## Develop

### `luciole init [dir]`

Creates an app in `dir`, which must be absent or empty. Default: `my-luciole-app`. The app is
a copy of Notes with its own `package.json`, a `tsconfig.json` extending
`@luciole-sh/core/tsconfig`, Oxlint, Oxfmt and VS Code settings, and `.bun-version`. Then run
`bun install` and `bun run dev` in it.

How `init` makes the app depends on where `luciole` runs from:

| `luciole` runs from                                           | `init` runs                                                   | The app's `@luciole-sh/core`                                                          |
| ------------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| An installed package (<code>{commands.fromNpm}</code> too)    | `bunx @luciole-sh/create@<version>`, at the CLI's own version | `^<version>`, from npm                                                                |
| A clone of the repository (<code>{commands.fromClone}</code>) | `packages/create/scripts/stage.ts --workspace`                | `file:` the clone's `packages/core`; other workspace packages are copied to `vendor/` |

A `file:` dependency ties the app to the clone, which has to stay where it is.

### `luciole dev [--app dir] [-- app arguments]`

Builds the app, starts its Server and Client, and rebuilds when you save a `.ts`, `.tsx`,
`.js` or `.jsx` file. Saves under `.luciole/` and `node_modules/`, and to `routeTree.gen.ts`, do
not count.

After each save:

- A build error shows in the running Client, which stays usable.
- A good rebuild restarts both processes. The Client reopens the same page with its history,
  its named fields and its token, the string it sends to prove who signed in.
- The app's arguments are checked again. `-- --help` prints them.

The run ends with the Client:

- Quitting the Client stops the Server too.
- `luciole dev` exits with the Client's exit code, or with 1 if a signal killed the Client. A
  host that runs it can tell a crash from a quit.
- A Client that exits during a rebuild ends nothing.
- SIGINT, SIGTERM and SIGHUP stop both processes, and `luciole dev` exits with 0. A closed
  terminal or an unmounted `<Terminal>` sends SIGHUP.

The pieces of this supervision are public as
[`@luciole-sh/core/dev`](/docs/reference/api/#supervising-an-app-luciole-shcoredev).

### `luciole devtools [--listen 1|<socket>|ws://host:port] [--demo] [--replay file.json] [--env]`

Starts the [DevTools](/docs/guides/devtools/). `--env` prints the variables the inspected
app's shell needs instead.

## Build

### `luciole build [options]`

| Option                                  | Effect                                                                                                    |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `--app dir`                             | The app to build (default: the current directory).                                                        |
| `--app-bundle`                          | Fail if the app bundle (`.luciole/app/`) cannot be produced, instead of warning.                          |
| `--sign-bundle`                         | Sign the app bundle's manifest with the publisher key (`luciole keys`); implies `--app-bundle`.           |
| `--web`                                 | Add `.luciole/web/`, the browser runtime served by the Server.                                            |
| `--web-local`                           | Add a static site where the Server runs in the browser too.                                               |
| `--compile`                             | Compile a single executable: Client and Server (see below).                                               |
| `--name n`                              | The binary's name (default: the app's directory name).                                                    |
| `--client-only`                         | Compile the Client alone.                                                                                 |
| `--target t`                            | Another platform, such as `bun-linux-x64` or `bun-linux-x64-musl`.                                        |
| `--runtime official\|host\|<bun>`       | The Bun runtime to embed: the official one of the target (default), the one running the build, or a path. |
| `--portable`                            | Make the host-runtime warning an error, for a binary meant for other machines.                            |
| `--native-dir dir`                      | Native packages installed for the target, for a cross-compiled Server.                                    |
| `--outfile f`                           | Where to write the binary.                                                                                |
| `--sign identity`, `--notarize profile` | Sign the macOS binary with a Developer ID, then notarize it.                                              |

Every option from `--name` down belongs to `--compile`: without it, `luciole build --name x` is a
usage error, never silently ignored.

Details: [build and distribution](/docs/reference/build-and-distribution/).

### `luciole runtime [--target t]`

Downloads the official Bun runtime of a target into the cache `--compile` uses, ahead of
time.

### `luciole web-runtime`

Prepares this framework version's web runtime ahead of `luciole build --web` (it needs git,
the network and Zig 0.16.0).

### `luciole keys [generate]`

Prints the publisher key that signs app bundles (its file, `SHA256:` fingerprint and public
key), or generates one. Not Apple's Developer ID.

### `luciole pack --package <npm name> --version <v> [--description d] [--outdir dir] <binary>…`

Makes npm packages from compiled binaries of one build: one per platform, and the main
package that points to them. It prints the order to publish them in, platforms first.

## Run

### `luciole <target>`

```text
luciole [<path | app | npm spec | git source> [--yes] [--url url]
       | <server url…> [--inline | --sandbox] [--allow-…] [--yes]]
```

Resolves the target and launches it ([opening an app](/docs/guides/opening-an-app/)). A built
directory (a path or a git source) also takes `--grace <duration>`, and the app's own
options. `--yes` accepts installs and new repositories without asking. URLs take the
sandbox flags of [apps you did not write](/docs/guides/untrusted-apps/#capabilities).

### `luciole example [name] [--yes] [-- app arguments]`

Runs an example app of this release, taken from the git tag `v<version>` of the luciole
repository. It needs git and the network:

- Without a name, it lists the examples that tag holds.
- With a name, it launches `examples/<name>` at that tag as a git source
  ([opening an app](/docs/guides/opening-an-app/)). An unknown name is refused with the list.
- The launcher asks before running a repository. `--yes` accepts.
- What follows `--` goes to the app, a `--yes` there included.

`LUCIOLE_EXAMPLES_REPO`, a git URL, takes the examples from another repository, such as a
fork. A development version has no tag, so it has no examples to list.

To run Notes without installing luciole:

### `luciolex <target>`

Like `luciole <target>`, but the target is never read as a subcommand, like `npx`:
`luciolex build` launches the app named `build`.

### `luciole start --role server|client [--app dir] [--url URL] [--artifact dir] [-- app arguments]`

Runs a built role in production (`NODE_ENV=production`): the Server (the default role), or
the Client joining `--url`. Without `--url`, the Client looks for its Server as
[usual](/docs/guides/opening-an-app/#joining-a-server-that-already-runs). The app's
arguments go to the Server only.

### `luciole connect <url | ssh://[user@]host[/port]> [--app dir] [--artifact dir]`

Runs the built Client against a URL, `ssh://` included. `--artifact dir` runs the Client
built in `dir` instead of the one in `<app>/.luciole/client`.

### `luciole trust <server url> <SHA256:fingerprint>`

Pins a publisher key for an origin opened by URL, out of band, replacing the pinned one.

## Installed apps

Apps installed from the npm registry live in `$XDG_DATA_HOME/luciole/apps/`.

| Command                           | Effect                                         |
| --------------------------------- | ---------------------------------------------- |
| `luciole search [text]`           | Apps (keyword `luciole-app`) matching the text |
| `luciole install <spec>… [--yes]` | Installs, or switches to the version given     |
| `luciole update [app…]`           | Each app to the latest version of its range    |
| `luciole list`                    | Installed apps                                 |
| `luciole remove <app>…`           | Removes the app and its binaries               |

<Note>
  A compiled app binary has its own commands (`serve`, `--url`, `--on`, `--new`, `--version`): see
  [opening an app](/docs/guides/opening-an-app/#as-a-single-binary).
</Note>
