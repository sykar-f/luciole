A luciole app is a directory of files, and each file runs on one side: the Client or the
Server. This page goes through Notes, the starter that `luciole init` copies, so you know what
each file of a new app is for. Notes is a list of notes, an editor, and SQLite on the Server.

A file's directory and its first line say which side runs it.

## Which side runs each file?

| File                           | Side   | What it does                                                                           |
| ------------------------------ | ------ | -------------------------------------------------------------------------------------- |
| `app/layout.tsx`               | Client | The persistent window: the sidebar, its search and the rail it folds into.             |
| `app/page.tsx`                 | Server | The screen before you choose a note: what to do next.                                  |
| `app/notes/[id]/page.tsx`      | Server | Loads a note, and passes the save and lookup Server Functions to the editor as props.  |
| `app/notes/[id]/loading.tsx`   | Client | Shown as soon as you click a note, until the page arrives.                             |
| `app/notes/[id]/not-found.tsx` | Client | A deleted note, or one that never existed.                                             |
| `app/error.tsx`                | Client | A page that failed to load: why, and a button to try again.                            |
| `app/routeTree.gen.ts`         | —      | The typed route tree, written by the build. Committed, never edited.                   |
| `components/Sidebar.tsx`       | Client | Search, selection and navigation, handled in the Client.                               |
| `components/notes-list.ts`     | Client | The sidebar's notes, read through a Server Function and again after each change.       |
| `components/NoteEditor.tsx`    | Client | Every keystroke, the Markdown view, autosave, the restored text.                       |
| `components/NoteFrame.tsx`     | Client | No directive: it runs on the side of its importers, the editor and the loading screen. |
| `components/StatusLine.tsx`    | Client | The line above the title: connection, save, router, one message at a time.             |
| `components/draft.ts`          | Client | Notes' own policy: unsaved text in memory, and saves whose outcome is unknown.         |
| `actions/notes.ts`             | Server | Server Functions, `"use server"`: `saveNote`, `getOperation`, `listNotes` and more.    |
| `server/repository.ts`         | Server | SQLite, ownership checks and transactions.                                             |
| `server/schemas.ts`            | Server | Zod schemas for the arguments the Server receives.                                     |
| `server/queries.ts`            | Server | Reads cached with `"use cache"`, tagged.                                               |
| `server/tags.ts`               | Server | The cache tags of those reads.                                                         |

Three optional files are absent from Notes:

- `server/auth.ts`, an identity adapter: see [authentication](/docs/concepts/authentication/).
- `server/cache.ts`, the cache handler: see [caching](/docs/concepts/cache/#where-entries-live).
- `app/args.ts`, which declares command-line options: see
  [app arguments](/docs/reference/app-arguments/).

You write no RPC protocol, no module registry and no OpenTUI bootstrap: the build and the
framework provide them.

## What happens when you save a note?

1. The note's page runs on the Server. It reads the note, and passes `saveNote` to the editor:

  mark={["saveAction={saveNote}"]}
  tone="server"
  caption="The page passes saveNote to the editor as a prop. The Client receives a reference to it."
/>

2. The editor handles each key in the Client. About a second after you stop typing, it calls
   `send`. With autosave off, **Save** calls it.

<Excerpt
  path="examples/notes/components/NoteEditor.tsx"
  find="send = () =>"
  count={2}
  mark={["saveAction(snapshot)"]}
  tone="client"
  caption="send calls the saveNote reference through two pieces of code, described below."
/>

`send` goes through two pieces of code before the request leaves:

- `save`, from Notes' draft store in `components/draft.ts`, keeps the unsaved text in memory
  until the Server confirms the save.
- `fields.submit`, from the framework, forgets the note's restored text before the request
  leaves. A Client killed during the save does not send it twice: see
  [send a form without sending it twice](/docs/concepts/session-restore/#send-a-form-without-sending-it-twice).

3. The framework sends the call as `POST /action`. On the Server, `saveNote` validates its
   argument, saves, and declares what changed:

<Excerpt
  path="examples/notes/actions/notes.ts"
  find="export async function saveNote"
  until="^}"
  mark={["SnapshotInput.parse", "await changed"]}
  tone="server"
  caption="saveNote checks its argument with Zod, saves, then invalidates the tags of what changed."
/>

4. The repository writes the note and the operation's result in one SQLite transaction. That
   transaction lets the **Check again** button look up a save whose response was lost.

5. The response carries the result and the invalidated tags. The Client reloads the routes that
   read those tags, and the editor marks the text as saved.

[What happens during a call](/docs/concepts/server-functions/#what-happens-during-a-call)
draws this save as a sequence of messages.

## What the framework does not do for you

The atomic save and the lookup of a lost result are Notes' own code. The framework does not
guarantee that a save runs exactly once, and the transport never retries a call. A call whose
response is lost fails as `unknown`, and Notes decides what comes next. `tests/http-transport.test.ts`
checks both:

- A failed call sends one request, whatever its outcome.
- A call that runs past its timeout fails as `unknown`, while the Server finishes it.

When a save's outcome is unknown, Notes looks the operation up on the Server:

- If the Server has the result, the save is settled.
- If the Server has no result, Notes sends the save again with the same ID. The repository
  applies an ID at most once.
- If that fails too, the save stays unknown.

`tests/transport.test.tsx` checks this lookup on Notes:

- It stops the Server right after a save commits. Notes then looks the save up, and SQLite
  holds the operation once.
- It sends one save twice with the same ID, and gets the first result back.
