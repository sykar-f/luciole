`luciole init` copies Notes, so this is what a new app starts from: a list of notes, an
editor, SQLite on the Server. Each file sits on one side; the directory it is in and its
first line say which.

## The files

| File                           | Side   | What it does                                                                         |
| ------------------------------ | ------ | ------------------------------------------------------------------------------------ |
| `app/layout.tsx`               | Client | The persistent window: the sidebar, its search and the rail it folds into.           |
| `app/page.tsx`                 | Server | No note chosen yet: what to do next.                                                 |
| `app/notes/[id]/page.tsx`      | Server | Loads a note and hands the save and lookup actions to the editor as props.           |
| `app/notes/[id]/loading.tsx`   | Client | Shown the moment a note is clicked, while the page travels.                          |
| `app/notes/[id]/not-found.tsx` | Client | A deleted note, or one that never was.                                               |
| `app/error.tsx`                | Client | A page that failed to load: why, and a button to try again.                          |
| `app/routeTree.gen.ts`         | —      | The typed route tree, written by the build. Committed, never edited.                 |
| `components/Sidebar.tsx`       | Client | Search, selection and navigation, handled in the terminal.                           |
| `components/notes-list.ts`     | Client | The sidebar's notes, read through a Server Function and again after each change.     |
| `components/NoteEditor.tsx`    | Client | Every keystroke, the Markdown view, autosave, the restorable field.                  |
| `components/NoteFrame.tsx`     | Client | No directive: shared by the editor and the loading screen, it follows its importers. |
| `components/StatusLine.tsx`    | Client | The line above the title: connection, save, router, one message at a time.           |
| `components/draft.ts`          | Client | Notes' own policy: Drafts in memory, saves whose outcome is unknown.                 |
| `actions/notes.ts`             | Server | Server Functions, `"use server"`: `saveNote`, `getOperation`, `listNotes` and more.  |
| `server/repository.ts`         | Server | SQLite, ownership checks and transactions.                                           |
| `server/schemas.ts`            | Server | Zod schemas for the arguments the Server receives.                                   |
| `server/queries.ts`            | Server | Reads cached with `"use cache"`, tagged.                                             |
| `server/tags.ts`               | Server | The cache tags of those reads.                                                       |

Two optional files are absent from Notes: `server/auth.ts`, an identity adapter
([authentication](/docs/concepts/authentication/)), and `server/cache.ts`, the cache handler
([caching](/docs/concepts/cache/#where-entries-live)). `app/args.ts` declares command-line
options ([app arguments](/docs/reference/app-arguments/)).

You write no RPC protocol, module registry, Flight manifest or OpenTUI bootstrap.

## A save, from the key to SQLite

1. The page of a note, on the Server, reads the note and passes `saveNote` to the editor:

  until="/>"
  mark={["saveAction={saveNote}"]}
  tone="server"
/>

2. The editor handles each key locally. About a second after typing stops (or on **Save**
   when autosave is off), it calls `send`, which calls the reference through Notes' Draft
   store and the restored-field group:

<Excerpt
  path="examples/notes/components/NoteEditor.tsx"
  find="send = () =>"
  count={2}
  mark={["saveAction(snapshot)"]}
  tone="client"
/>

3. The framework encodes the call with Flight and sends `POST /action`. On the Server,
   `saveNote` validates its argument, saves, and declares what changed:

<Excerpt
  path="examples/notes/actions/notes.ts"
  find="export async function saveNote"
  until="^}"
  mark={["SnapshotInput.parse", "await changed"]}
  tone="server"
/>

4. The repository writes the note and the operation's result in one SQLite transaction:
   that is what lets the **Check again** button look up a save whose response was lost.

5. The response carries the result and the invalidated tags. The Client revalidates the
   routes that read them; the editor confirms its Draft.

<Note>
  The atomic save and the lookup of a lost result are Notes' own code, not a framework guarantee of
  exactly-once delivery. If no result is found, the operation stays unknown and is not replayed.
</Note>
