One library, `src/launcher/`, opens an app wherever it comes from: `luciole <target>`,
`luciolex <target>` and the binaries the build compiles all go through it. From a clone, write
`bun packages/luciole/src/cli.ts` where this page writes `luciole`.

| Target                               | Example                                  | What happens                                                        |
| ------------------------------------ | ---------------------------------------- | ------------------------------------------------------------------- |
| a path (`./`, `../`, `/`, `~/`, `.`) | `luciole ./examples/notes`               | build, then a local launch                                          |
| an installed app                     | `luciole notes`                          | its binary                                                          |
| an npm spec                          | `luciole @ada/notes@^1.2`                | installed after confirmation if missing, then launched              |
| a git source                         | `luciole github:ada/tools#v1/apps/notes` | fetch, trust, install, build (cached), local launch                 |
| a Server URL                         | `luciole https://notes.example.com`      | the generic Client: signed bundle, pinned key, `sandbox` by default |

A bare word (`notes`) is an installed app if there is one, else an npm spec. A relative path
without `./` is refused with that hint rather than guessed. `luciole` alone opens the
launcher, an app that lists installed apps and searches the registry. `luciolex build`
launches the app named `build`: `luciolex` never reads its target as a subcommand.

## On this machine

```sh
luciole ./my-app
```

The launcher builds the directory and starts its Server on a **Unix socket** (mode `0600`,
in a `0700` directory of the user), not a port: no port conflict, and no one else can
connect. Two launches of the same target share one Server, by default. The Server runs in
the directory the command was typed in, so Notes creates `notes.sqlite` there; what it
writes goes to `$XDG_STATE_HOME/luciole/<app>/server.log`, never to the Client's screen.

The Server outlives the Client for a grace period (15 minutes by default, `--grace <duration>`,
`0` stops at once): a Client that crashes and comes back finds the same Server, its
state, its route and its named fields. Quitting with <kbd>Ctrl+C</kbd> stops it at once when
it was the last Client. How launches share a Server is the app's choice
([`luciole.server`](/docs/reference/package-json/#server-and-grace)).

During development, `luciole dev --app <dir>` builds, starts both processes, and rebuilds on
every change; the Client reopens the same page ([session restore](/docs/concepts/session-restore/)).
It ends when the Client does, with the Client's exit code, and stops both processes on SIGINT,
SIGTERM or SIGHUP ([CLI](/docs/reference/cli/#luciole-dev---app-dir----app-arguments)).

## Joining a Server that already runs

A Client finds its Server in this order: `--url`, then `LUCIOLE_URL`, then the user's file
`$XDG_CONFIG_HOME/luciole/<app>.json` (`~/.config/luciole/notes.json` for Notes), then
`http://127.0.0.1:3000`. The file holds only the URL; an unreadable file, or one without
`url`, stops the Client with a message rather than being ignored.

```json
{ "url": "ssh://alice@notes.example.com" }
```

With built artifacts, the two roles start separately:

```sh
luciole build
luciole start --role server
luciole start --role client --url http://127.0.0.1:3000   # in another terminal
```

### Over SSH

An `ssh://` URL opens the tunnel itself; the Server keeps listening on loopback.

```sh
luciole connect ssh://alice@notes.example.com            # Server on 127.0.0.1:3000 there
luciole connect ssh://alice@notes.example.com:2222/4000  # ssh on 2222, Server on 4000
luciole connect ssh://alice@bastion/10.0.0.5:3000        # Server reached from the ssh host
```

The form is `ssh://[user@]host[:ssh-port][/[remote-host:]remote-port]`. Before taking the
terminal, the Client runs `ssh -N -o ExitOnForwardFailure=yes -L <socket>:127.0.0.1:3000 …`:
keys, agent, `~/.ssh/config`, `ProxyJump` and host key checking stay OpenSSH's, and a
passphrase is typed as usual. The tunnel ends on a Unix socket in a private temporary
directory, not a local port, and closes when the Client quits.

A connection failure shows `ssh`'s message and stops the Client. A later cut is a network
error like any other (`not-sent` or `unknown`); this tunnel does not reconnect by itself.
`ssh` (OpenSSH) must be in the terminal machine's `PATH`, and a Client killed with SIGKILL
leaves its `ssh` process behind.

## On another machine, over SSH

A compiled binary starts its Server on a host and its Client here:

```sh
notes --on build-box
```

1. One master ssh connection authenticates once; the probe, the upload and the Server
   reuse it (`LUCIOLE_SSH` replaces `ssh`).
2. The host reports its OS, architecture and libc, and whether this build is already
   installed under `~/.local/share/luciole/apps/<app>/<buildId>/`.
3. If not, or if it no longer matches its `SHA256SUMS`, the binary uploads itself when the
   host's platform is its own, or the one given with `--target`, whose identity must be the
   same app, the same build and the host's platform. The archive is checked, then swapped
   in whole. A tampered build is refused, never started.
4. `<app> serve --detach` finds the managed Server of this launch on the host, or starts
   one detached from ssh. The app's options reach it on standard input, never on a command
   line other users could read with `ps`.
5. A tunnel `ssh -N -L <local socket>:<remote socket>` joins it to the Client.

**If the connection drops** while the Client lives, its pings fail and it shows
"Disconnected". The tunnel is relaunched after 1 s, 2 s, 4 s… up to 30 s, on the same local
socket and without prompting (`BatchMode`); when it holds again the Client shows "Connected",
with the same Server, route and state. Conditions: key or agent authentication (a
password-only login cannot come back by itself, relaunch the Client), and the Server still in
its grace period.

## From a git source

```sh
luciole github:ada/tools#v1/apps/notes
```

Accepted forms: `github:user/repo[#ref][/dir]`, `gitlab:…`,
`https://github.com/user/repo[/tree/ref/dir]`, `git+https://…`, `git+ssh://…`, `git+file://…`.
A repository is arbitrary code, its Server included: at the first launch the launcher shows
the URL and the commit (sha, subject, author, date) and asks for confirmation **before**
installing and building. A new commit of an accepted repository launches after a short
summary of the new commits. A `package.json` without `bun.lock` is refused rather than
resolved on the day. Dependencies' lifecycle scripts do not run unless the app lists them
in `trustedDependencies`, as Bun does by default.

## By URL, in the generic Client

```sh
luciole https://notes.example.com
```

The Server publishes a signed bundle of its Client code (`GET /manifest`,
`GET /bundle/<sha256>`); the generic Client checks the signature, pins the publisher's key
on first use, and opens the app in a tab, **sandboxed** by default where the sandbox also
confines the network. Several URLs open several tabs. What the modes mean and what they
enforce: [apps you did not write](/docs/guides/untrusted-apps/).

## In a browser

The browser is one more host: it evaluates the same app bundle against a web runtime,
OpenTUI compiled to WebAssembly and drawn by xterm.js.

| Build                       | Server                                       | For                                   |
| --------------------------- | -------------------------------------------- | ------------------------------------- |
| `luciole build --web`       | the usual Server, which also serves the page | opening a hosted app from a link      |
| `luciole build --web-local` | the same handler, in a SharedWorker          | a static site, a demo, an offline app |

**`--web`**: the Server serves the page under `/_luciole/web/` to **one declared origin**:

```sh
luciole build --web
LUCIOLE_WEB_ORIGIN=https://notes.example.com PORT=3000 bun --conditions=react-server .luciole/server/index.js
```

The first build prepares the web runtime once per framework version (it clones OpenTUI and
compiles it with Zig 0.16.0; `luciole web-runtime` does it ahead of time). Without
`LUCIOLE_WEB_ORIGIN` there is no web route, and the Server keeps refusing any request that
carries a browser `Origin`. Authentication is unchanged; the bearer stays in memory.

**`--web-local`** writes a static site into `.luciole/web/`, to serve from any static host
(`application/wasm` for `.wasm` files). The Server runs in a SharedWorker shared by every tab
of the origin; its SQLite databases live in memory and are written to OPFS before each
Server Function answers. The Server code may use `bun:sqlite` (a subset), `Bun.sleep`,
`crypto` and same-origin `fetch`; `fs`, `child_process`, `Bun.spawn` and `Bun.Terminal` fail
with a message, and such apps keep `--web`. `<Terminal>` shows an "unavailable here" screen.
The site's own demos are built this way.

## As a single binary

```sh
luciole build --compile
```

One executable per OS and architecture, with the Bun runtime, OpenTUI's native library and
the build ID inside: the machine that runs it needs neither Bun nor `node_modules`. By
default it holds the Client **and** the Server, business code included, and the build warns
that whoever receives it can read that code; `--client-only` keeps the Server out, for
users who only connect to yours.

| Command                                          | Role                                              |
| ------------------------------------------------ | ------------------------------------------------- |
| `notes [options]`                                | both, here; the Server on a private socket        |
| `notes serve [--http [host]:port \| --socket p]` | the Server alone                                  |
| `notes --url <url>`                              | the Client alone                                  |
| `notes --on [user@]host[:port]`                  | the Server on the host, the Client here, over ssh |
| `notes --new`                                    | a fresh launch, without reclaiming a session      |
| `notes --version`                                | the app, the build ID and the target              |

Targets, runtimes, signing and notarization for macOS, glibc and musl:
[build and distribution](/docs/reference/build-and-distribution/).

<Note>
  Whatever the way in, the app's own options (`app/args.ts`) configure its Server. They are refused
  with `--url`, `luciole connect` and the generic Client, which join a Server that is already
  configured ([app arguments](/docs/reference/app-arguments/)).
</Note>
