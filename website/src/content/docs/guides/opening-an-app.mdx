`luciole <target>` opens an app from wherever it comes: a directory, an installed app, an npm
package, a git repository or a Server URL. Find the section that matches where the app is and
where you are. From a clone of the repository, write `bun packages/core/src/cli.ts` where this
page writes `luciole`.

| Target                               | Example                                  | What happens                                                        |
| ------------------------------------ | ---------------------------------------- | ------------------------------------------------------------------- |
| a path (`./`, `../`, `/`, `~/`, `.`) | `luciole ./examples/notes`               | build, then a local launch                                          |
| an installed app                     | `luciole notes`                          | its binary                                                          |
| an npm spec                          | `luciole @ada/notes@^1.2`                | installed after confirmation if missing, then launched              |
| a git source                         | `luciole github:ada/tools#v1/apps/notes` | fetch, trust, install, build (cached), local launch                 |
| a Server URL                         | `luciole https://notes.example.com`      | the generic Client: signed bundle, pinned key, `sandbox` by default |

How `luciole` reads a target:

- A bare word such as `notes` is an installed app if there is one, else an npm spec.
- A relative path without `./` is refused, with a hint to add it.
- `luciole` alone opens the app list: the installed apps, and a search of the registry.
- `luciolex build` launches the app named `build`. `luciolex` never reads its target as a
  subcommand.

Each task below places the Client and the Server on a machine:

| Task                                                                        | The Client runs             | The Server runs                         | Between them             |
| --------------------------------------------------------------------------- | --------------------------- | --------------------------------------- | ------------------------ |
| [Open an app on this machine](#open-an-app-on-this-machine)                 | here                        | here                                    | a private Unix socket    |
| [Join a Server that already runs](#join-a-server-that-already-runs)         | here                        | wherever it was started                 | HTTP, or your SSH tunnel |
| [Start the Server on another machine](#start-the-server-on-another-machine) | here                        | on the remote machine                   | an SSH tunnel            |
| [Open a Server URL](#open-a-server-url-in-the-generic-client)               | here, in the generic Client | at that URL                             | HTTPS                    |
| [Open an app in a browser](#open-an-app-in-a-browser)                       | in a browser tab            | on your Server, or in the tab's browser | HTTP, or nothing         |

## Open an app on this machine

```sh
luciole ./my-app
```

The app opens in your terminal window. Behind it, the launcher builds the directory and starts
its Server:

- The Server listens on a **Unix socket** in a private directory, not on a port. No port can
  conflict, and no other user can connect.
- The Server runs in the directory you typed the command in. Notes creates `notes.sqlite`
  there.
- Its output goes to `$XDG_STATE_HOME/luciole/<app>/server.log`, not to your screen.
- Two launches of the same target share one Server, unless the app
  [chooses otherwise](/docs/reference/package-json/#choose-which-launches-share-a-server).

When the Client exits, the Server stays up for a **grace period**: 15 minutes by default. A
Client that crashes and comes back in time finds the same Server, state, route and named
fields. Set the period with `--grace <duration>`, where `0` stops the Server at once.

<kbd>Ctrl+C</kbd> stops it at once when you quit the last Client.

While you work on the app, use `luciole dev --app <dir>` instead. It rebuilds on every change,
and the Client reopens the same page ([session restore](/docs/concepts/session-restore/)). See
[`luciole dev`](/docs/reference/cli/#luciole-dev---app-dir----app-arguments) for its exit code
and signals.

## Join a Server that already runs

A Client takes the first Server URL it finds, in this order:

1. `--url <url>` on the command line
2. the `LUCIOLE_URL` environment variable
3. your file `$XDG_CONFIG_HOME/luciole/<app>.json`, such as `~/.config/luciole/notes.json`
4. `http://127.0.0.1:3000`

The file holds only the URL:

```json
{ "url": "ssh://alice@notes.example.com" }
```

The Client stops with a message when that file cannot be read, or has no `url`.

### Start the Client and the Server separately

Run these commands from the app's directory, or add `--app <dir>`:

```sh
luciole build
luciole start --role server
luciole start --role client --url http://127.0.0.1:3000   # in another terminal
```

The Server runs until you stop it. A Client can quit and join it again.

### Join a Server over SSH

An `ssh://` URL opens an SSH tunnel to a Server that only listens on loopback:

```sh
luciole connect ssh://alice@notes.example.com            # Server on 127.0.0.1:3000 there
luciole connect ssh://alice@notes.example.com:2222/4000  # ssh on 2222, Server on 4000
luciole connect ssh://alice@bastion/10.0.0.5:3000        # Server reached from the ssh host
```

The form is `ssh://[user@]host[:ssh-port][/[remote-host:]remote-port]`. What to expect:

- luciole runs your OpenSSH `ssh`, which must be in your `PATH`. Your keys, agent,
  `~/.ssh/config`, `ProxyJump` and host key checks apply as usual.
- A passphrase prompt shows before the app takes the screen.
- The tunnel ends on a private Unix socket on your machine, not on a local port. It closes
  when the Client quits.
- If `ssh` fails to connect, the Client prints `ssh`'s message and stops.

<Note kind="warning">
  This tunnel does not reconnect. A later cut is a network error like any other, with the outcome
  `not-sent` or `unknown`. A Client killed with SIGKILL leaves its `ssh` process behind.
</Note>

[Troubleshooting](/docs/reference/troubleshooting/#the-ssh-tunnel-fails) explains each `ssh` failure and its fix.

## Start the Server on another machine

A compiled binary starts its Server on a remote machine and its Client here:

```sh

```

so it takes longer.

### Reconnect after the connection drops

The Client reconnects by itself when both hold:

- `ssh` logs in with a key or an agent.
- The Server is still in its grace period.

When the connection drops, the Client shows "Disconnected". It relaunches the tunnel after 1 s,
then 2 s, 4 s, and up to 30 s between tries. Once the tunnel holds, the Client shows
"Connected", with the same Server, route and state.

A relaunched tunnel never prompts. After a password-only login, quit and relaunch the Client.

## Open an app from a git repository

```sh
luciole github:ada/tools#v1/apps/notes
```

Accepted forms: `github:user/repo[#ref][/dir]`, `gitlab:…`,
`https://github.com/user/repo[/tree/ref/dir]`, `git+https://…`, `git+ssh://…`, `git+file://…`.

A repository is arbitrary code, its Server included, so the launcher asks first:

- At the first launch, it shows the URL and the commit: sha, subject, author and date. It asks
  you to confirm **before** it installs and builds.
- When an accepted repository has new commits, it shows a short summary of them, then
  launches.
- It refuses a `package.json` without `bun.lock`, rather than resolve versions on the day.
- Dependencies' lifecycle scripts run only when the app lists them in `trustedDependencies`,
  as Bun does by default.

## Open a Server URL in the generic Client

```sh
luciole https://notes.example.com
```

The app opens in a tab of the generic Client, a Client that runs any app's code it downloads.
What happens on the way:

- The Server publishes a signed bundle of its Client code.
- The generic Client checks the signature, and remembers the publisher's key at the first
  visit.
- The tab is **sandboxed** by default, and the sandbox also confines the network.

Several URLs open several tabs. What each mode allows, and how to choose it:
[apps you did not write](/docs/guides/untrusted-apps/).

## Open an app in a browser

A browser runs the same app bundle, drawn in the page by xterm.js. Two builds exist:

| Build                       | Where the Server runs                        | For                                   |
| --------------------------- | -------------------------------------------- | ------------------------------------- |
| `luciole build --web`       | the usual Server, which also serves the page | opening a hosted app from a link      |
| `luciole build --web-local` | the same Server code, in a browser Worker    | a static site, a demo, an offline app |

The first build prepares the web runtime. It needs the network, `git` and Zig 0.16.0, on your
`PATH` or in `ZIG`. To prepare it ahead of time, run `luciole web-runtime`.

The page holds the web runtime: luciole's Client, React, xterm.js and OpenTUI compiled to
WebAssembly. Your app's bundle is the one a terminal Client runs, unchanged:

### Serve the app from your Server

From the app's directory:

```sh
luciole build --web
LUCIOLE_WEB_ORIGIN=https://notes.example.com PORT=3000 bun --conditions=react-server .luciole/server/index.js
```

Open `https://notes.example.com/_luciole/web/` in a browser. The Server serves the page to one
origin only, the one `LUCIOLE_WEB_ORIGIN` names.

- Without `LUCIOLE_WEB_ORIGIN`, the Server has no web route. It refuses every request that
  carries a browser `Origin`.
- Sign-in works as in a terminal Client. The page keeps the bearer token, the string the
  Client sends with each request to prove who signed in, in memory only.
- With `LUCIOLE_WEB_ORIGIN` set, the Server refuses to start when the build has no web runtime,
  or one built for another ABI. Run `luciole build --web` again.

### Publish a static site

`luciole build --web-local` writes a static site into `.luciole/web/`. Serve it from any static
host, with `application/wasm` for `.wasm` files. The site's own demos are built this way.

The Server runs in a SharedWorker, shared by every tab of the origin that runs this build. A
browser without SharedWorker runs the Server in a dedicated Worker, and then only one tab at a
time can open the app.

What the Server code can do there:

| Works                                         | Does nothing                   | Fails                                                                        |
| --------------------------------------------- | ------------------------------ | ---------------------------------------------------------------------------- |
| `bun:sqlite` (a subset), in memory            | writing a file                 | `rename`, `copyFile`, `symlink`, `mkdtemp`, opening a file to write: `EROFS` |
| `Bun.sleep`, `crypto`, same-origin `fetch`    | making or removing a directory | `child_process`, `Bun.spawn`, `Bun.Terminal`, with a message                 |
| `fs` reads of the files in `server-seed.json` |                                |                                                                              |

SQLite databases live in memory. The Server saves them to the browser's storage (OPFS) before
each Server Function answers. A `<Terminal>` shows an "unavailable here" screen.

An app that needs a process, a terminal or a real disk keeps `--web`.

<Note>
  The DevTools do not attach to an app in a browser. Inspect the app in a terminal, with the same
  code.
</Note>

## Hand someone a single binary

`luciole build --compile` writes the app as one executable, which runs on a machine without Bun.
To compile it, hand it over, update it and roll it back, follow
[ship a binary](/docs/guides/ship-a-binary/).

A binary opens the app in these ways:

| Command                                          | What it runs                                       |
| ------------------------------------------------ | -------------------------------------------------- |
| `notes [options]`                                | both here, the Server on a private socket          |
| `notes serve [--http [host]:port \| --socket p]` | the Server alone                                   |
| `notes --url <url>`                              | the Client alone                                   |
| `notes --on [user@]host[:port]`                  | the Server on the remote machine, the Client here  |
| `notes --new`                                    | a new launch, instead of reattaching a crashed one |
| `notes --version`                                | prints the app, the build ID and the target        |

<Note>
  Whatever the way in, the app's own options (`app/args.ts`) configure its Server. They are refused
  with `--url`, `luciole connect` and the generic Client, which join a Server that is already
  configured ([app arguments](/docs/reference/app-arguments/)).
</Note>
