luciole can slow down and break the network between your Client and your Server. You then
see the loading screens, the pending states and the error handling before your users do. On
your machine the Server answers in a millisecond, and an app that mishandles a slow or lost
request still looks fine.

## Add a round trip to every request

<CopyCommand lines={[`${envPrefix}_LATENCY_MS=500 bun run dev`]} />

`LUCIOLE_LATENCY_MS` adds a round trip to every app request: page renders, navigations,
Server Functions, refreshes and lookups.

- A value of `500` waits 250 ms before sending and 250 ms before delivering the response.
- Each request waits on its own, and the wait counts against the request's timeout.
- Real latency comes on top of it.
- Default: `0`.

## Add jitter, slow streams and faults

| Variable                 | Effect                                                                                          |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| `LUCIOLE_JITTER_MS`      | A random extra delay, from 0 to this value, on each direction of each request.                  |
| `LUCIOLE_CHUNK_DELAY_MS` | A delay before each chunk of a response reaches the decoder: slow streams, `Suspense` included. |
| `LUCIOLE_FAULT`          | Faults, each with a probability: `refuse:0.1,drop:0.05,cut:0.05`.                               |

The three faults, and the outcome the app receives for each:

| Fault    | What happens                                                  | Outcome    |
| -------- | ------------------------------------------------------------- | ---------- |
| `refuse` | The request is never sent.                                    | `not-sent` |
| `drop`   | The Server answers, and the response is lost: the Server ran. | `unknown`  |
| `cut`    | The body fails before its first byte.                         | `unknown`  |

## What does Notes show when a save fails?

Run Notes with lost responses:

<CopyCommand lines={[`${envPrefix}_LATENCY_MS=300 ${envPrefix}_FAULT=drop:0.3 bun run dev`]} />

With a lost response, the Server may have written the note. Notes says nothing at first. A
second later, it asks the Server what happened to that save. It sends the save again only if
the Server has no trace of it
([Server Functions](/docs/concepts/server-functions/#when-a-call-fails)).

If the save is still not settled after 3 seconds, the line above the title says so:

| Situation                      | Message                                               | Button          |
| ------------------------------ | ----------------------------------------------------- | --------------- |
| The outcome is unknown         | "Save not confirmed. Your text is kept here."         | **Check again** |
| The save could not be sent     | "Could not reach the Server. Your text is kept here." | **Retry**       |
| The connection is lost as well | "○ Disconnected. Your text is kept here."             | **Reconnect**   |

A lost connection is the usual case, and its message replaces the other two. Notes keeps
retrying by itself, at longer and longer intervals. The message goes away once a retry
succeeds. Press <kbd>Ctrl+T</kbd> to watch the requests.

## What the app should do with each outcome

- `not-sent` and `rejected`: nothing ran on the Server. It is safe to say "not saved" and
  let the user try again.
- `unknown`: the Server Function may have run, and running it again may do it twice. Look it
  up, or let the user decide. An idempotent operation ID, stored with the result, makes the
  lookup possible.

The transport never retries a call: it reports what it knows, and the app decides.
`tests/http-transport.test.ts` checks that a failed call sends one request, whatever its
outcome.

## See the requests

- Notes binds <kbd>Ctrl+T</kbd> to `<DebugOverlay />`. It shows the requests, the open
  requests, the bytes, the last round trip and the latest events.
- The [DevTools](/docs/guides/devtools/) draw a waterfall of the Client's and the Server's
  requests. Their Conditions panel changes latency, jitter, chunk delay and faults while the
  app runs. The variables set them at startup only.
- `useApplication().onEvent(listener)` receives each transport event for your own logs:
  `request`, `response`, `chunk`, `end`, and `error` with its outcome.

<Note kind="warning">
  This is a simulation per request, not a TCP emulation: no bandwidth, no packet loss. It assumes
  the Client runs on your machine. Running the Client itself over SSH adds a round trip to every
  key, which this does not model.
</Note>

## Set the latency from a web page

A page that embeds the web runtime in an `iframe` of its own origin can set the round trip
and the next request's fault by message. The landing page's Notes demo does:

```ts
iframe.contentWindow.postMessage(
  { source: "luciole", type: "network", latencyMs: 500, fault: "drop" },
  origin,
);
```

The runtime answers with the transport's events, as `{ source: "luciole", type: "event",
event }`. A page draws a request timeline from them. See
[opening an app](/docs/guides/opening-an-app/#open-an-app-in-a-browser).
