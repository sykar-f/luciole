The DevTools show what a running luciole app does, as Chrome DevTools and React DevTools do
for a web page. They run in a second terminal pane, next to the app you inspect. Open them
when a screen is slow, renders too often or shows stale data.

To try them without an app, run the DevTools demo on the
[Examples](/examples/#devtools) page.

## Start the DevTools next to your app

Open two terminal panes at the repository's root:

<CopyCommand label="pane 1: the DevTools" lines={[`${commands.fromClone} devtools`]} />

<CopyCommand
  label="pane 2: the app you inspect"
  lines={[`eval "$(${commands.fromClone} devtools --env)"`, "bun run dev"]}
/>

`--env` prints the two variables to export:

| Variable           | Role                                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------- |
| `LUCIOLE_DEVTOOLS` | Where the DevTools listen. The Client and the Server both read it.                                      |
| `BUN_OPTIONS`      | Preloads `src/devtools/hook.ts`, the hook the Components panel needs. The other panels work without it. |

`LUCIOLE_DEVTOOLS` takes one of three addresses:

- `1`, the default Unix socket of your user
- a socket path, `/…` or `unix:/…`
- `ws://host:port`

`luciole devtools` listens on its `--listen` flag first. Without the flag, it listens on the
shell's `LUCIOLE_DEVTOOLS`, then on the default socket. Two more flags open other sources:

- `--demo` replays a scripted run of Notes.
- `--replay file.json` opens a recording.

Without `LUCIOLE_DEVTOOLS`, the app does not load the DevTools. Its Server keeps the
instrumentation you configured, and its Client never imports the DevTools agent. Under
`NODE_ENV=production` (`luciole start`), both processes ignore the variable and print a
warning.

## Move around with the keyboard

These keys work in every panel:

| Key                                                    | Action                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------- |
| <kbd>1</kbd> to <kbd>7</kbd>                           | Open that panel.                                                    |
| <kbd>Tab</kbd>, <kbd>Shift+Tab</kbd>                   | Open the next or the previous panel.                                |
| <kbd>j</kbd>, <kbd>k</kbd>, <kbd>↓</kbd>, <kbd>↑</kbd> | Select the next or the previous line.                               |
| <kbd>g</kbd>                                           | Select the first line.                                              |
| <kbd>Shift+G</kbd>                                     | Follow the newest line of a live list.                              |
| <kbd>p</kbd>                                           | Pause. The DevTools keep the events and apply them when you resume. |
| <kbd>Shift+C</kbd>                                     | Clear the events.                                                   |
| <kbd>Shift+E</kbd>                                     | Export a recording.                                                 |

The bottom line of each panel lists its own keys, then these.

## What does each panel show?

| Panel        | What it shows                                                                                              |
| ------------ | ---------------------------------------------------------------------------------------------------------- |
| 1 Network    | One line per request of the Client and the Server, with its timing, its cause and the cache that answered. |
| 2 Components | The Client's component tree, how often each component rendered, and why it rendered last.                  |
| 3 Console    | The `console.*` output of both processes. A Server line carries the `callId` of its request.               |
| 4 Router     | The location, the rendered and cached matches, their status, age, params and search.                       |
| 5 Cache      | The Server cache's entries, with their function, tags, age, hits, misses and invalidations.                |
| 6 Input      | The keys the app received, with their modifiers and sequences.                                             |
| 7 Conditions | The Client's network conditions, which you change while the app runs.                                      |

### Read the Network panel

<Screen
  frame="devtools-network"
  caption="The Network panel of the DevTools demo, on a scripted run of Notes, with the watch stream selected."
  regions={[

    { id: "2", side: "server", rects: [{ row: 1, col: 24, rows: 1, cols: 17 }] },
    { id: "3", side: "client", rects: [{ row: 3, col: 0, rows: 11, cols: 100 }] },
    { id: "4", side: "server", rects: [{ row: 23, col: 1, rows: 1, cols: 43 }] },
  ]}
  marks
>

1. `client notes 4101`: the inspected Client, with its app and process ID. `●` marks a
   connected process. The demo shows `○`, because no app is connected.
2. `server notes 4100`: the inspected Server.
3. The requests, one line each. A line joins the Client's request and the Server's work
   through their shared `callId`. Its columns give the cause (`nav`, `pre`, `ref`, `inv`,
   `act`, `live`), the cache that answered (`mem`, `hit`, `miss`, `stale`, `part`) and the
   time. The bar on the right draws the six series its header names:
   - `░` queued and `▒` waiting, on the Client
   - `█` the Server's work
   - `━` the stream, with a `╋` for each chunk
   - `◆` an answer from a cache on the Client, with no request
4. `Server: request +2ms · headers +4ms · end –`: the Server's own timing of the selected
   request. `watch` is a live stream, so it has no end yet.

</Screen>

The panel flags two patterns in the first column:

- `↳` marks a **sequential waterfall**. The request left less than 25 ms after another
  request's response, so it probably waited for that response.
- `⟳` marks a **double invalidation**. One cause rendered the same page twice, for instance
  the Server's `invalidate()` and a component's, after the same Server Function.

In this panel, <kbd>f</kbd> filters the lines and <kbd>z</kbd> zooms on the last 60 s, 10 s
or 2 s. <kbd>o</kbd> opens the console, filtered on the selected request.

  ]}
  marks
>

1. The Client's component tree, from `Layout` to `KeyHelp`. `×3` counts the renders, and
   `props: note` names what changed at the last one.
2. `◇ NotePage Server`: a Server Component. In development, the panel shows the Server
   Components that the Server's stream describes, above the Client components they produced.
3. `⚠ unnecessary`: an **unnecessary render**. The props, the state and the context are
   equal, as `memo()` compares them, so the component rendered only because its parent did.
4. The selected component: its render count, the reason of its last render, its size and
   position, its props and its hooks.

</Screen>

In this panel, these keys act on the components:

- <kbd>u</kbd> shows only the unnecessary renders.
- <kbd>h</kbd> flashes the components that render in the app's own pane. The outline is drawn after
  layout, so the app's layout does not move.
- <kbd>o</kbd> opens the selected component's source in `$VISUAL` or `$EDITOR`.

The build adds the names, the source locations and the hook names. It annotates each
component and custom hook of your app and of the framework. Hooks from packages are not
annotated: when the panel cannot match a hook, it shows no name rather than a wrong one.

### Purge a cache tag

In the Cache panel, <kbd>t</kbd> picks a tag of the selected entry, and <kbd>x</kbd>
invalidates that tag. Outside a request, this purges **the Server cache only**. No Client is
told: each Client gets fresh data at its next render of the route.

### Change the network conditions

The Conditions panel changes the Client's latency, jitter, chunk delay and fault
probabilities while the app runs. The variables of
[Latency and faults](/docs/guides/latency-and-faults/) set the same conditions, at startup
only. The DevTools add their latency before a request is sent, so Network shows it as
waiting.

## Export a recording and replay it

<kbd>Shift+E</kbd> writes two files in the directory the DevTools run in:

- `luciole-devtools-<date>.json`, the raw events, which `--replay` opens
- a HAR 1.2 file, which Chrome's tools read. What HTTP cannot say goes in `_luciole` fields.

## Keep the DevTools local

The DevTools can invalidate, refresh, change the network conditions, flash components and
purge a Server cache tag. Purging a tag is the only command that changes the Server's state.
These are development commands, so keep the listener on your machine:

- The default socket is in `$XDG_RUNTIME_DIR`, or in macOS's private `tmpdir()`. Its name
  holds your user ID, and its mode is `0600`.
- With `ws://`, the listener refuses any request that carries an `Origin` header, so a web
  page cannot drive the app.
- With `ws://`, the listener listens on the host you give. Give a local one.

## Run React DevTools alongside

```sh
npx react-devtools        # the standalone interface
DEV=true bun run dev      # OpenTUI loads react-devtools-core and connects
```

The DevTools hook chains React DevTools' own hook instead of replacing it. Both receive every
commit.

## Check that it works

Open Notes with the DevTools attached, edit a note and wait a second for its autosave.
Network shows an `act` line for `saveNote`. Components shows a higher render count on
`NoteEditor`.

If Network fills and Components stays empty, the Client started without the preload. Run the
`eval` line of pane 2 again in that pane, then restart the app.

<Note>
  The DevTools are for development. Several Clients connected at once mix their trees and routers in
  the panels. The Cache panel does not invalidate Clients yet.
</Note>
