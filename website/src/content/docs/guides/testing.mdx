Check that your app works, from the build to a real terminal. luciole ships no testing library
yet. This page gives the four levels the repository tests itself with, and which of them your
app can use:

| Level           | Tool                                          | What it catches                               | Can your app use it?                           |
| --------------- | --------------------------------------------- | --------------------------------------------- | ---------------------------------------------- |
| The build       | `luciole build`, `bun run verify`             | code on the wrong side, bad routes, bad types | yes                                            |
| In-process      | `bun test`, `createApplication`, `testRender` | screens, restores, failed requests            | yes. The repository's helpers are not exported |
| A bad network   | `LUCIOLE_LATENCY_MS` and the other variables  | work that waits on the network                | yes                                            |
| A real terminal | the journeys of `scripts/pty/`                | what a user sees and types                    | only inside the repository                     |

## Let the build catch boundary errors

`luciole build` refuses what would be wrong at run time, and names the file and line. It fails
on:

- a module that crosses the boundary between Client and Server
- a Server Function that is not a named async declaration
- two routes with the same URL
- a `"use cache"` closure
- a React Client hook in a page

Each error points where the mistake is, relative to the app. A syntax error gives the parser's
line and column. An import that names no file points at that import:
`app/page.tsx:2:1: Cannot resolve ../components/Header`.

In a starter, `bun run verify` runs the type check, lint, format check and build together:

<CopyCommand lines={["bun run verify"]} />

The type check covers navigation too. `app/routeTree.gen.ts` makes a link to a route that does
not exist a TypeScript error, and so is a missing param.

## Drive the Client in-process with `bun test`

The Client is an ordinary object that a test drives without a terminal:

- `createApplication` takes a `transport` or a `fetch`, which stands between the Client and the
  Server.
- `app.restoration.snapshot()` returns the restored session that a restart would reopen.
  `createApplication({ session })` restores one.
- OpenTUI's `testRender` draws the `Shell` in memory and types into it.

The repository restarts Notes this way. The second run refuses saves, to check that unsent
text is kept:

On the Server, `createHandler(config, options)` from `@luciole-sh/core/server` is the Server as
a function of a `Request`, without listening. `@luciole-sh/core/build` builds an app from a
test.

<Note kind="warning">
  These entries are public: `@luciole-sh/core/client`, `@luciole-sh/core/server` and
  `@luciole-sh/core/build`. The helpers that the repository's tests build on them are not exported.
  `tests/helpers.ts` imports a built Client and launches a Server, for instance. An app outside the
  repository writes its own.
</Note>

## Test under a bad network

Every test that drives a real Client can set the transport's conditions, with
`LUCIOLE_LATENCY_MS`, `LUCIOLE_JITTER_MS`, `LUCIOLE_CHUNK_DELAY_MS` and `LUCIOLE_FAULT`. See
[latency and faults](/docs/guides/latency-and-faults/).

`tests/latency.test.tsx` adds 500 ms of latency. It checks that typing, scrolling and hover
still send no request.

## Script a journey in a real terminal

A **journey** is a script of what a user does, played against the real app. The repository's journeys run a production Client on
a real pseudo-terminal, `Bun.Terminal`, and rebuild the screen with OpenTUI's terminal
emulator. They answer the queries a Client sends at startup, and read only complete frames.

Most examples have a journey. Three of them:

<CopyCommand lines={["bun run test:pty", "bun run test:pty:restore", "bun run test:pty:forge"]} />

A journey reads like what a user does: wait for a text, press keys, send a signal.

<Note>
  The journey driver, `scripts/pty/driver.ts`, belongs to the repository's scripts, not to the
  package. An app in this repository can add a journey next to the others. An app outside it cannot
  import the driver.
</Note>

## What the repository proves, and what it does not

`bun run verify` at the root runs types, lint, format, tests and the build. CI runs on macOS and
Linux at every push, and runs the Linux sandbox in containers.

`docs/VALIDATION.md`, in French, lists what each test proves and its known limits. The
[status page](/status/) summarises them.

See also [latency and faults](/docs/guides/latency-and-faults/),
[session restore](/docs/concepts/session-restore/) and the
[API reference](/docs/reference/api/).
