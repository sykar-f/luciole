Each `page.tsx` under `app/` is a page, and its directory is its URL. The build turns these
files into the routes of [TanStack Router](https://tanstack.com/router). TanStack Router then
decides every navigation in the Client: which route matches, its params, its layouts, its
loading state and its cancellation.

## Which file draws what

| File            | Side   | Role                                                                                                  |
| --------------- | ------ | ----------------------------------------------------------------------------------------------------- |
| `page.tsx`      | Server | The page of this directory's URL. Never enters the Client bundle.                                     |
| `layout.tsx`    | Client | Wraps every page below it and stays mounted between them. `app/layout.tsx` is required.               |
| `loading.tsx`   | Client | Shown in place of the page while it loads ([loading and errors](/docs/concepts/loading-and-errors/)). |
| `error.tsx`     | Client | Shown in place of a page that failed to load or render.                                               |
| `not-found.tsx` | Client | Shown when a page calls `notFound()`, and for a URL no page matches (`app/not-found.tsx`).            |

A layout, loading, error or not-found file must declare `"use client"` and a default
export, or the build fails with the file and line. A layout receives `{ children, params }`.
Its `children` is where the routes below it render.

A loading, error or not-found file takes the place of the page only. The layouts around the
page stay on screen:

## How directory names become URLs

| Directory name | Meaning                                                                                                    |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| `notes`        | A static segment. Static routes win over dynamic ones at the same level.                                   |
| `[id]`         | A param: `params.id` in the page, `useParams()` in the Client.                                             |
| `[...name]`    | A catch-all of one or more segments (`params.name` is `guide/install/linux`). Last in the path, no layout. |
| `(group)`      | Not in the URL. With a `layout.tsx`, a layout without a path segment.                                      |

Forge's pages show each kind of segment at work:

| File under `app/`                                  | URL                             | Why                                                     |
| -------------------------------------------------- | ------------------------------- | ------------------------------------------------------- |
| `(public)/login/page.tsx`                          | `/login`                        | `(public)` is a group, so only `login` reaches the URL. |
| `(app)/page.tsx`                                   | `/`                             | `(app)` is a group too. Its `layout.tsx` wraps the app. |
| `(app)/repos/[repo]/page.tsx`                      | `/repos/payments`               | `[repo]` is a param: `params.repo` is `"payments"`.     |
| `(app)/repos/[repo]/pulls/new/page.tsx`            | `/repos/payments/pulls/new`     | The static `new` wins over the param `[number]`.        |
| `(app)/repos/[repo]/pulls/[number]/page.tsx`       | `/repos/payments/pulls/1`       | Two params: `repo` and `number`.                        |
| `(app)/repos/[repo]/pulls/[number]/files/page.tsx` | `/repos/payments/pulls/1/files` | A static segment after the params.                      |

The login page sits outside `(app)`, so the layout of `(app)/layout.tsx` does not wrap it.

The build fails, and names the files, when it finds:

- two pages with the same URL once groups are removed
- two equivalent dynamic patterns, such as `/users/[id]` and `/users/[slug]`
- a repeated param
- a malformed segment

Optional params (`[[...name]]`) are not supported, and a layout is always a Client Component.

## Keep state across pages with a layout

A layout stays mounted as long as the destination is under its segment. Its local state,
focus and scroll survive navigations between its pages. Notes' root layout renders the
sidebar, so the search typed in it stays while one note after another opens:

## Navigate from a Client Component

The build writes `app/routeTree.gen.ts`. Commit it and do not edit it. It registers the app's
routes with TanStack, so TypeScript checks `to`, `params` and `useParams` against this app's
files. A route that does not exist, or a missing param, is a TypeScript error.

Navigate with the hooks that `@luciole-sh/core/client` re-exports. luciole does not
re-export TanStack's `<Link>`, because `<Link>` renders a DOM anchor.

<Excerpt
  path="examples/notes/components/commands.ts"
  find="export function useCommands()"
  until="open: (id: string) => void open(id),"
  mark={["navigate("]}
  tone="client"
/>

- The last navigation wins. A navigation that replaces another aborts the other's loader,
  and a late response never changes the screen.
- The loading screen shows at once. <kbd>Esc</kbd> (`useApplication().cancel()`) goes back
  to the last resolved route without reloading it.
- `refresh()` reloads the current route. The tree stays mounted while it does, so a field
  keeps its focus and its text.

## Read search params

Every page accepts search params, as **strings**, like a URL's (`"42"` stays `"42"`). Each
search is a separate page, rendered by the Server and cached apart. Back and forward restore
it.

```tsx
void navigate({ to: "/repos/$repo", params: { repo }, search: { state: "merged" } });

// The page, on the Server
export default function Page({
  params,
  searchParams,
}: {
  params: { repo: string };
  searchParams: Record<string, string>;
}) {}
```

The Server answers `400` to search params beyond these limits:

- at most 32 keys
- each key matches `[\w.-]{1,64}`
- each value holds up to 1,000 characters

`useSearch()` reads them in the Client. A filter that must answer every keystroke stays local
state.

## Preload a page before it opens

`useRouter().preloadRoute({ to, params })` renders a page in the background. The next
navigation to it shows it without waiting for the network, while the preloaded tree is
fresh. TanStack's `preloadStaleTime` sets that time to 30 s. Preloading goes through the
same loader, so authentication and cache purges apply.

## Send values after the page with a `Promise` or an iterable

A page can pass a Client Component a `Promise`, read with `use()` under `Suspense`. It can
also pass an async iterable. Flight delivers both in the same response as they resolve. The
transport's timeout only bounds the wait for the start of the page.

For a stream tied to what the screen shows, prefer
[`useLive`](/docs/concepts/server-functions/#live-server-functions). An async iterable is
read once, and the router can mount a cached tree again.

<Note>
  The Server does no path matching. It receives a route ID and params, and checks both on every
  render. It answers `404` to an unknown route, and `400` to missing, extra or non-text params. A
  protected page answers `401` without a sign-in session.
</Note>
