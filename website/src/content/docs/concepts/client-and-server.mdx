luciole is a React Server Components framework for terminal apps. You write one app, and its
build produces two programs:

- the **Server** renders pages, runs Server Functions and keeps the data;
- the **Client** runs in the user's terminal, draws with [OpenTUI](https://github.com/anomalyco/opentui)
  and handles every key, scroll and hover itself.

Typing and scrolling never wait for the network. The Client calls the Server only to load a
page or to run a Server Function. `tests/latency.test.tsx` checks this under 500 ms of
simulated latency.

## What travels between the Client and the Server

The Client sends two kinds of requests:

- `GET /render` asks for a page;
- `POST /action` runs a Server Function.

The Server answers both in [React Flight](https://react.dev/reference/rsc/server-components),
React's serialization of a rendered tree. Here is a minute of Notes, the example app, as the
two programs see it:

## What each side contains

| Program | Contains                                                                                            | Never contains                                  |
| ------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| Client  | the runtime that draws in a terminal, TanStack Router, the keymap, **this app's** Client Components | Server pages, Server Functions' code, `server/` |
| Server  | the HTTP runtime, the routes, the Server Functions and the business code                            | OpenTUI                                         |

Three rules decide where a module runs:

- pages run on the Server;
- a file marked `"use client"`, and what it imports, runs on the Client;
- `server-only` or `client-only` pins a module to one side.

[Client Components](/docs/concepts/client-components/) gives the details.
`luciole build` writes both programs into the app's `.luciole/` directory:
[its outputs](/docs/reference/build-and-distribution/#what-luciole-build-writes) are listed in the
Reference.

<Note>
  The Client and the Server both run on Bun. A module that reads a file or starts a process runs on
  either side without an error. On the wrong side, it acts on the wrong machine. Mark it
  `server-only` or `client-only`.
</Note>

## Why both sides come from one build

Both programs must come from **the same build**. Each build has an ID, a hash of everything
the build reads ([the list](/docs/reference/build-and-distribution/#how-the-build-id-is-made)).

- The Client sends that ID with every request, in `x-luciole-build`.
- A Server of another build refuses the request with a `409`.
- The Client keeps what it already shows.

Two tests check this:

- `tests/http-transport.test.ts`: a page load carries the build ID. A `409` fails both a page
  load and a Server Function call as an incompatible build.
- `tests/transport.test.tsx`: the Server answers an old build ID with a `409`. The status then
  reads "Incompatible build", and an open editor keeps its text.

The hash includes `bun.lock`, which lists the packages of every platform. A Linux Server and a
macOS Client compiled from the same sources therefore share one build ID.
[`--on`](/docs/guides/opening-an-app/#start-the-server-on-another-machine) relies on that.
