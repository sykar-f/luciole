A Client Component is a module that starts with `"use client"`. The Client runs it on the
user's machine, so no network round trip slows it down. It holds every key, the focus,
scrolling, local state and loading animations.

Client Components are ordinary React components that render OpenTUI elements, such as `box`,
`text`, `input`, `select` and `scrollbox`. Layouts, loading, error and not-found files are
always Client Components.

## Where does the boundary fall?

`"use client"` marks where the Server's imports stop. The Server does not run that module.
A page that imports it receives a **reference** to it instead, one for each exported value.
The module joins the Client's bundle, with everything it imports, directly or not.

Notes' note page shows both sides of the boundary:

<Excerpt

/>

<Excerpt

  find='"use client"'
  until="./ui-state"
  mark={['"use client"', 'from "./NoteFrame"', 'from "../actions/notes"']}

/>

`"use client"` counts only at the very top of the file, before any other statement. An
import of types only, such as `import type { MouseEvent }`, pulls nothing into either bundle.

<details>
<summary>How the build finds the directive</summary>

The build reads the module's prologue through the TypeScript AST: the string statements
before the first other statement. No regular expression rewrites the source. For each
runtime export of a `"use client"` module, the build writes a Client Reference. The Client's
bundle registers the modules those references point to.

</details>

## Bind your own keys

The framework binds two keys, in the `luciole` group:

- <kbd>Ctrl+C</kbd> quits the app.
- <kbd>Esc</kbd> cancels a navigation in progress.

Every other key belongs to the app. Bind it with `useBindings`, OpenTUI's keymap that
`@luciole-sh/core/client` re-exports. Notes is driven by the pointer, and its editor adds
shortcuts that the screen does not list:

<Excerpt
  path="examples/notes/components/NoteEditor.tsx"
  find="useBindings("
  until="[editing, focus, canSave, failing, draft]"
  mark={['key: "ctrl+s"']}
  tone="client"
  caption="Notes' editor binds Ctrl+S to save, and Ctrl+E to start or stop editing."
/>

A layer of bindings lives with its component: leaving a page removes its keys and their help.
`<KeyHelp inline groups={["note"]} />` draws that help from the active bindings that declare a
`desc`. Notes declares none. OpenTUI's `useKeyboard` still works beside the keymap.

## Keep a module on one side

| What you want                          | How                                                           |
| -------------------------------------- | ------------------------------------------------------------- |
| A component the Server renders         | `"use client"`: the boundary. The Server receives a reference |
| Code that must never reach the Client  | `import "server-only"`, or a file under `server/`             |
| Code that must never run on the Server | `import "client-only"`                                        |

`"use client"` and `client-only` do different jobs:

- A page may import a `"use client"` module. It receives references from it.
- A module that imports `client-only` fails the build when a Server module imports it, directly
  or not, without a `"use client"` module in between.

`client-only` exists because both sides run on Bun. Code meant for the user's machine, such as
`$EDITOR`, `~/.config` or the clipboard, would not crash on the Server. It would act on the
wrong machine. Forge's editor launcher is the example in the repository:

<Excerpt
  path="examples/forge/components/editor.ts"
  find='import "client-only"'
  until="build refuses this module"
  mark={['import "client-only"']}
  tone="client"
  caption="Forge's editor launcher opens a file in the reviewer's own editor, so it imports client-only."
/>

The markers need no package. The build resolves them to empty modules, and
`@luciole-sh/core/tsconfig` declares them so that `tsc` accepts the import. There is no
`*.server.*` or `*.client.*` suffix.

The build refuses these among the modules the Client imports, directly or not:

- a module under `server/`
- a module that imports `server-only` or `@luciole-sh/core/server`
- a `"use cache"` module
- `require()` or a dynamic `import()` in the app's sources

## Use packages on either side

A Client Component imports any installed package without declaring it. The bundler takes the
package with its dependencies.

The markers work for packages too. The build fails when a package reaches the wrong side:

- a package that imports `server-only` or `@luciole-sh/core/server` reaches the Client
- a package that imports `client-only` reaches the Server

A third-party package that declares nothing can be kept on the Server's side. List it in an
optional `luciole.json`, next to the app's `package.json`:

```json
{ "serverPackages": ["@prisma/client", "bcrypt"] }
```

Every boundary error prints the whole chain, from the page:

```text
Client package db-client imports server-only: it is Server-only
  via app/page.tsx → components/widget.tsx → lib/format.ts → db-client/index.js → server-only
```

<Note kind="warning">
  These checks protect the boundary between Client and Server. They are not a sandbox: a package's
  code runs with the rights of its process. Built-ins such as `node:fs` do not choose a side either.
  A module that opens the Server's database must import `server-only`. Otherwise it is bundled into
  the Client, and it opens a database on the user's machine.
</Note>

## Which import paths does the build resolve?

- relative paths, with or without an extension
- subpath imports (`#name`), from the `imports` field of the nearest `package.json`. A subpath
  import counts for all its targets.

Path aliases from `tsconfig` do not resolve.
