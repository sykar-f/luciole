Every page and every `"use server"` module requires a session unless it says otherwise. The
framework carries the session; signing in, storing the token, renewing it and business
permissions stay with the app.

## Without `server/auth.ts`: one local user

An app without `server/auth.ts` has a **single-user** session: every request is the user
`LUCIOLE_USER` (`local` by default). `LUCIOLE_TOKEN`, set on both sides, protects it: the
Client sends it as `Authorization: Bearer …`, and a request without it has no session. Its
protected pages and Server Functions are refused; public ones still answer
([what answers without a session](/docs/reference/environment/#server)).

The Server listens on loopback by default. It refuses to listen elsewhere (`LUCIOLE_HOST`)
unless `LUCIOLE_TOKEN` or `server/auth.ts` is set. Before any public exposure, put it behind a
TLS reverse proxy and restrict network access to it; use an HTTPS URL so the token never
travels in clear. For a private connection, keep the loopback listener and connect over
[SSH](/docs/guides/opening-an-app/#over-ssh).

## With `server/auth.ts`

An app that replaces the local identity provides `server/auth.ts`. The build includes it in
the Server's graph only.

```ts
import type { AuthConfig } from "@luciole-sh/core/server";

export default {
  unauthorizedPath: "/login",
  async authenticate(request) {
    const token = request.headers.get("authorization")?.replace(/^Bearer /, "");
    return token ? await sessions.fromToken(token) : null;
  },
} satisfies AuthConfig;
```

`authenticate` returns the session or `null`. Pages, actions and repositories read it with
`getSession()` (`{ userId }`), or `getOptionalSession()`. That one returns the request's
session, or `null` for an anonymous request. A public page or Server Function still gets the
session of a signed-in user. Forge is the example in the repository that provides one.

## Public pages and actions

```tsx
export const auth = "public" as const;

export default function LoginPage() {
  return <text>Sign in</text>;
}
```

An action is protected independently of the page that hands out its reference. To allow a
Server Function without a session, put public actions in their own module; every function of
a module shares its policy:

```ts
"use server";
export const auth = "public" as const;

export async function beginLogin() {
  // Validate the arguments even without a session.
}
```

## What happens without a session

- A navigation to a protected route gets a `401`, then goes locally to `unauthorizedPath`,
  which must name an existing public route. So does a refresh of the current route.
- Without `unauthorizedPath`, a navigation still moves to the protected route. Its page slot
  shows the error, through the nearest `error.tsx`, inside the layouts that stay. The status
  is `Authentication required`.
- Without `unauthorizedPath`, a refresh that gets a `401` takes the page off the screen. Its
  page slot shows the error, as after a refused navigation. A refresh that fails for another
  reason, such as a lost connection, keeps the page and its unsaved text.
- A refused Server Function never navigates: the error reaches its caller, and
  `AuthenticationRequired.loginPath` says where to sign in.

## Signing in and out

`useApplication().setToken(token?)` replaces the token of the following requests. It purges
TanStack's route cache, and again at the end of a navigation in progress. A private page
cached under one token is never shown under another. Then it reloads the current routes
with the new token. After signing in or out, your app navigates where it wants.

Signing out on a protected page takes that page off the screen. The reload gets a `401`, and
the Client goes to `unauthorizedPath`. Without `unauthorizedPath`, the page slot shows the error,
inside the layouts that stay.

<Note kind="warning">
  The page leaves the screen with the unsaved text its components held. The Client does not keep
  that text, because keeping the page would leave the previous account's data on screen.
</Note>

Replacing a token also forgets the text of restorable fields
([session restore](/docs/concepts/session-restore/)). It touches no app state: an app that
changes identity clears its own unsaved text.

<Note kind="warning">
  Layouts are Client Components: they cannot call `getSession()`. Public session data the chrome
  needs (a display name, a role) comes from a page, or from a Client context the app provides; it
  never replaces the check on the Server. A Flight reference grants no right by itself, and a
  protected route never replaces the permission checks in the action or the repository.
</Note>

Never put a secret in the Client's sources or in a prop: both reach the terminal.
