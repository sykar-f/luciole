Every page and every `"use server"` module requires a **sign-in session** unless it opts out.
A sign-in session is who signed in, as the Server's `authenticate` returns it. luciole checks
it on the Server for each request, and your app handles the rest:

- signing in and storing the token
- renewing the token
- business permissions

## Use one local user without `server/auth.ts`

An app without `server/auth.ts` has a **single user**. Every request comes from
`LUCIOLE_USER`, which is `local` by default.

To protect that user, set `LUCIOLE_TOKEN` on both sides. It is the **bearer token**, the
string the Client sends with each request to prove who signed in. The Client sends it as
`Authorization: Bearer …`.

A request without the token has no sign-in session. Protected pages and Server Functions
refuse that request, and public ones still answer
([what answers without a sign-in session](/docs/reference/environment/#which-routes-answer-without-a-sign-in-session)).

The Server listens on loopback by default. It refuses any other address (`LUCIOLE_HOST`)
unless `LUCIOLE_TOKEN` or `server/auth.ts` is set.

<Note kind="warning">
  Before you expose the Server, put it behind a TLS reverse proxy and restrict network access to it.
  Use an HTTPS URL, so the token never travels in clear. For a private connection, keep the loopback
  address and connect over [SSH](/docs/guides/opening-an-app/#join-a-server-over-ssh).
</Note>

## Sign users in with `server/auth.ts`

To replace the single user, add `server/auth.ts`. The build puts it in the Server only. Its
default export has two fields:

- `authenticate(request)` returns the sign-in session, `{ userId }` and any fields you add,
  or `null`.
- `unauthorizedPath`, optional, names the public route where a refused page load goes. The
  Server does not start when that route is missing or protected.

Pages, Server Functions and repositories read the sign-in session in two ways:

- `getSession()` returns it, and throws `Authentication required` for an anonymous request.
- `getOptionalSession()` returns it, or `null` for an anonymous request.

A public page or Server Function still gets the sign-in session of a user who signed in.
Neither function works inside `"use cache"`. Pass the identity to the cached function as an
argument.

## Make a page or a Server Function public

A page opts out with `export const auth = "public"`:

```tsx
export const auth = "public" as const;

export default function LoginPage() {
  return <text>Sign in</text>;
}
```

A Server Function keeps its own policy, whatever the page that passes it. All functions of a
module share one policy, so put public Server Functions in a module of their own:

```ts
"use server";
export const auth = "public" as const;

export async function login(user: string, pin: string) {
  // Check the arguments: anyone can call this function.
}
```

`setToken` does four things, in this order:

1. When it replaces a token, it forgets the text of restorable fields
   ([session restore](/docs/concepts/session-restore/)). The first sign-in of a Client keeps
   that text, so text restored after a crash survives the sign-in it needs.
2. It sets the token of the following requests, or removes it.
3. It drops every cached private page, and again when a navigation in progress ends. A page
   loaded under one token never shows under another.
4. It reloads the current routes with the new token.

`setToken` does not navigate and touches no state of your app. After a sign-in or a
sign-out, your app navigates where it wants. When the user changes, your app also clears its
own unsaved text.

<Note kind="warning">
  Signing out on a protected page takes the page off the screen, with the unsaved text its
  components held. The Client does not keep that page, because it would leave the previous account's
  data on screen.
</Note>

## What does the user see when a request is refused?

A refused request gets a `401`. What the user sees depends on the request and on
`unauthorizedPath`. The last column is `useConnection().status`, which a status line shows.

| Request                                                            | With `unauthorizedPath`                                                                             | Without `unauthorizedPath`                                                                    | Status                                     |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------ |
| A navigation to a protected route                                  | The Client goes to `unauthorizedPath`.                                                              | The Client moves to the route. Its page slot shows the error through the nearest `error.tsx`. | `Authentication required`                  |
| A refresh of the current route, such as after `setToken`           | The Client goes to `unauthorizedPath`.                                                              | The page leaves the screen. Its page slot shows the error, as after a refused navigation.     | `Authentication required`                  |
| A Server Function call                                             | Nothing moves. The caller gets `AuthenticationRequired`, and its `loginPath` is `unauthorizedPath`. | Nothing moves. The caller gets `AuthenticationRequired`, and its `loginPath` is `undefined`.  | `Authentication required`                  |
| A refresh that fails for another reason, such as a lost connection | The page stays, with its unsaved text.                                                              | The page stays, with its unsaved text.                                                        | `Disconnected`, with the reason in `error` |

The status lasts until a request succeeds. After a redirect, the `unauthorizedPath` page loads
without error, so the status soon reads `Connected`.

When the page slot shows the error, the layouts stay on screen around it
([loading and errors](/docs/concepts/loading-and-errors/)).

## Keep permission checks on the Server

<Note kind="warning">
  A protected route or a Server Function reference grants no right by itself. Check permissions in
  the Server Function or the repository that reads the data.
</Note>

Layouts are Client Components, so they cannot call `getSession()`. A layout that shows a
display name or a role gets it from a page, or from a Client context your app provides. That
copy never replaces the check on the Server.

Secrets stay on the Server: see
[what a page cannot do](/docs/concepts/server-components/#what-a-page-cannot-do).
