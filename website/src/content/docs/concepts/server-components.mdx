A `page.tsx` is a Server Component by default. It runs in the Server process, reads data
directly (no API layer between the page and the database) and returns OpenTUI elements. The
Client receives the rendered tree, never the page's code.

The build accepts a page that starts with `"use client"`, and that page is a Client Component.
Its code goes into the Client, and the Server sends only a reference to it, with `params` and
`searchParams`. It cannot read data on the Server.

Keep the page on the Server, and move the interactive part into a Client Component that the
page renders. Notes does this below.

## What a page can do

- Be `async` and `await` anything: a query, a file, a model call.
- Read the sign-in session with `getSession()`, or `getOptionalSession()` on a public page.
- Read the app's command-line arguments with [`cli.get()`](/docs/reference/app-arguments/).
- Import Server Functions and Client Components, and pass them down as props.
- End with `notFound(what?)`, which shows the nearest `not-found.tsx`.
- Export `staleTime = 30`, in seconds, to let the router show its cached tree without asking
  again ([caching](/docs/concepts/cache/#show-a-page-without-a-request-with-staletime)).
- Export `auth = "public"` to make the page reachable without signing in
  ([authentication](/docs/concepts/authentication/)).

## What a page passes to the Client

A page composes Client Components and gives them props. Props travel in Flight, React's
serialization. A prop can be data, a promise, an async iterable or a reference to a Server
Function. The page of a note hands its editor the note and two Server Functions:

`saveAction` reaches the Client as a reference. Calling it sends a request to the Server,
which runs `saveNote` there ([Server Functions](/docs/concepts/server-functions/)).

## What a page cannot do

- Handle a key. A page is rendered on the Server, never mounted. Keys belong to Client
  Components.
- Use React's Client hooks and APIs: `useState`, `useEffect`, `createContext` and the other
  exports React leaves out of its `react-server` build. The build refuses the import and
  prints the fix, so the Server does not crash at start on a missing export:

  ```text
  app/page.tsx:1:19: useState is Client-only React: a Server Component cannot use it. Add "use client" at the top of this file, or move the part that needs it into a Client Component
    via app/page.tsx
  ```

- Be cached as a tree. `"use cache"` caches data, not components.

<Note kind="warning">
  Never put a secret in a prop. Everything a page passes to a Client Component is sent to the
  Client, where the person at the keyboard can read it.
</Note>

<Note kind="warning">
  An exception thrown while rendering reaches the nearest `error.tsx` as a render error, opaque in
  production. A page cannot rely on its message reaching the Client.
</Note>

## Why pages and not Server layouts

Layouts are Client Components that stay mounted. Only the page is rendered by the Server on
each navigation. Persistent Server layouts, with one Flight payload per segment, are not
supported.

A layout that needs data from the Server, such as a display name for its status line, gets
it in one of two ways:

- from a Server Function it calls, as the sidebar of Notes reads its list with `listNotes`;
- from a page;
- from a Client context the app provides.
