While a page loads, when it fails and when it does not exist, the Client shows a screen of
yours in the page's place. Only the page is replaced. The layouts around it stay mounted, with
their lists, fields and focus. A status in your layout tells the user when the Server is out
of reach.

## Show a screen while the page loads

A `loading.tsx` is the pending screen of every page below its directory. A page takes the
nearest one among its parents. The Client draws it at once, without waiting for the Server.
It receives the destination's `params`.

Without a `loading.tsx`, the Client shows "Connecting…" until the Server's first answer, then
"Loading…".

Give the loading screen the same layout as the page, or the page jumps when it arrives. The
framework cannot know the size of a Server page before it arrives, so this is your app's job.
Notes draws both with `components/NoteFrame.tsx`, in the same order:

- the status line
- the title, on one line, already known from the list the layout holds
- the note, or its placeholder

If the loading screen animates, change only colours or constant-width glyphs. Notes pulses the
placeholder's opacity with OpenTUI's `useTimeline` and stops it on unmount.

## Replace the page when it fails

An `error.tsx` replaces the page when loading or rendering it fails. A page takes the nearest
one among its parents, as for `loading.tsx`. Without one, the Client shows the error's message
in the page's place.

An `error.tsx` receives `{ error, path, params, retry }`:

- `error` is a `TransportError` with its `outcome`, or a Server render error. In production, the
  Client gets a generic error in place of the Server's message.
- `path` and `params` name the page that failed.
- `retry()` loads the page again.

What stays on screen depends on what failed:

| What failed                    | What the user sees                                                        |
| ------------------------------ | ------------------------------------------------------------------------- |
| A navigation                   | `error.tsx` in the page's place, with the layouts still mounted           |
| A refresh                      | The current page, still mounted, and the reason in `useConnection()`      |
| A refresh refused with a `401` | Not the current page, dropped as it shows what the user may no longer see |

A refresh refused with a `401` follows the rules of
[authentication](/docs/concepts/authentication/#what-does-the-user-see-when-a-request-is-refused).

Each error screen, yours or the default one, also emits a `failure` event. The event carries
the page's `path` and the error's `message`, and you receive it through
`useApplication().onEvent`. A Client started by `luciole dev` or by a host forwards it to that
parent, which learns which page failed and why. See
[`@luciole-sh/core/dev`](/docs/reference/api/#supervising-an-app-luciole-shcoredev).

## Answer a page that does not exist

A page calls `notFound(what?)` from `@luciole-sh/core/server` to end its render. The Client then
shows the nearest `not-found.tsx`, which receives `{ path, params, what }`. `app/not-found.tsx`
also answers a URL that no page matches.

A missing page is an answer, not a failure. The status stays "Connected", and the Client emits
no `failure` event.

## Show the connection in your layout

The framework draws no header and no status bar. `useConnection()` gives your layout what it
needs:

- `status`, one of the five values below
- `error`, why the last refresh failed, cleared by the next success
- `buildError`, a failed rebuild under `luciole dev`
- `refresh`, which reloads the page
- `activity`, one of `connect`, `navigate`, `refresh` or `idle`

| `status`                  | When                                                                   |
| ------------------------- | ---------------------------------------------------------------------- |
| "Connecting"              | Before the Server's first answer                                       |
| "Connected"               | The last request got an answer, a missing page included                |
| "Disconnected"            | The last request failed, most often because the Server is out of reach |
| "Incompatible build"      | The Server runs another build and refused the request with a `409`     |
| "Authentication required" | The Server refused the request with a `401`                            |

[Troubleshooting](/docs/reference/troubleshooting/#connecting-the-client) gives the cause and the
fix of each status.

Notes shows one message at a time, on the status line above the note's title, the line its save
uses too. The messages come in this order:

1. a lost connection, with a **Reconnect** button
2. the page's own message, such as a save in trouble
3. what the router is doing: "Opening…" with **Cancel**, "Connecting…" or "Syncing…"

A lost connection and a refresh each appear only after a short delay. The line stays still
while all goes well, and does not flash after every save.

## Cancel or refresh a navigation

- <kbd>Esc</kbd> during a navigation goes back to the last resolved route, without reloading it.
  `useApplication().cancel()` does the same, as Notes' **Cancel** button does.
- `refresh()` reloads the destination in progress, or the mounted route. During a refresh the
  tree stays mounted, and `activity` is `refresh`. Fields keep their focus and text.
- The key and the control for `refresh()` are your app's choice. The examples bind it to
  <kbd>Ctrl+R</kbd>, and Notes to a **Reconnect** button while offline.
- A `401` sends the user to the app's `unauthorizedPath`, if it declares one, without rendering
  protected content. See [authentication](/docs/concepts/authentication/).
- A `409` means the Server runs another build and refused the request before decoding it. The
  Client empties the router's cache. `tests/transport.test.tsx` checks the order: a body the
  Server cannot decode still gets a `409` from another build.

<Note>
  Loading screens are Client Components on purpose, so that they show without the network. A loading
  screen that needs data from the Server is a page, and would wait for that data.
</Note>
