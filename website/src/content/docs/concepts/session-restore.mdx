The Client keeps a restored session, as a browser does, so a crash or a rebuild does not lose
what the user typed. For each history entry, it keeps:

- the text typed into named fields
- which named field had the focus
- how far named scroll boxes were scrolled

Nothing else is kept:

- Page data comes back from the Server when the Client opens the page again.
- The bearer token, the string the Client sends with each request to prove who signed in, stays
  with your app.
- A field without a `name`, such as a PIN or a password, is never written.

The next Client takes a file only when:

- the Client that wrote the file is dead
- the file was written for the same Server key
- the file is the newest of those left

The Server key names the app, not the socket address, which changes at every launch:

| How the app was opened          | Server key                                           |
| ------------------------------- | ---------------------------------------------------- |
| `luciole ./notes`, a directory  | `local:<directory>`                                  |
| `luciole github:ada/tools#v1/…` | `git:<repository>`, with the path inside it          |
| `notes`, a compiled binary      | `local:notes`                                        |
| `notes --on build-box`          | `ssh:build-box/notes`                                |
| `luciole connect`, `--url`      | the URL, so these Clients never take the files above |

The launcher also adds the app's arguments to the key. When the app's Server is not shared, it
adds the current directory too
([how long a Server lives](/docs/reference/build-and-distribution/#how-long-a-server-lives)).
`--new` starts without a restored session.

<details>
<summary>How two Clients starting at once share the files</summary>

Each Client renames the file it takes, so of two Clients that start together, one gets the
file and the other moves on to the next one. The winner writes its own process ID into the file
at once, so that a third Client sees it alive.

</details>

## What happens to my text?

| Event                                                                | What is kept                                                               | Where                                                   | What the user sees                                          |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------- |
| Going back to a history entry, with `u` in Files, Forge and Mdreader | That entry's field text, focus and scroll positions                        | The Client's memory and the restored session's file     | The fields as the user left them                            |
| A refresh, with `refresh()`                                          | The whole page, which stays mounted                                        | On screen                                               | The same fields, with their focus and text                  |
| A rebuild under `luciole dev`                                        | The page, the history, each entry's state and the token                    | The restored session's file, and `luciole dev`'s memory | The same screen, running the new code                       |
| A crash, `kill -9`, a closed terminal or an SSH cut                  | The page, the history and each entry's state                               | The restored session's file, read at the next launch    | The next Client opens on the same page, its fields filled   |
| SIGTERM at shutdown, in a desktop window too                         | The page, the history and each entry's state                               | The restored session's file, read at the next launch    | The next Client opens on the same page, its fields filled   |
| A sign-out or another account, with `setToken`                       | The focus and scroll positions, but no field text                          | The restored session's file                             | Empty fields                                                |
| A Client's first sign-in                                             | Everything                                                                 | The restored session's file                             | The text restored after a crash, after the sign-in it asked |
| Sending a group with `submit`                                        | Nothing of the group's text, unless the request did not run or was refused | Removed from the file at once                           | A next Client without the sent text                         |
| <kbd>Ctrl+C</kbd> or `app.quit()`, quitting on purpose               | Nothing                                                                    | The file is deleted, as for a browser closed on purpose | A next launch with no restored text                         |
| Closing a desktop window, which quits the app                        | Nothing                                                                    | The file is deleted                                     | A next launch with no restored text                         |

Three rules decide which entry holds the text:

- **Text is kept per history entry**, as in a browser. Opening the same page again from a link
  creates a new, empty entry. To keep text per document whatever the path, your app stores it
  itself, as Notes and Forge do with their drafts.
- **A field belongs to the entry where it was mounted.** A field in a persistent layout keeps
  writing to the entry where it appeared.
- **Restoring is retyping.** On mount, a field whose entry holds text calls `onInput` or
  `onChange` once with it. Your app's state, or its form library's, receives it as typing, as
  unsaved text. Only typed text is kept. A value your app sets, such as a reset, only follows
  text already kept.

<Note kind="warning">
  Unsaved text that your app holds only in memory is lost on every exit and on every rebuild. There
  is no Fast Refresh.
</Note>

## Name a field to keep its text

`<Input>` and `<Textarea>` from `@luciole-sh/core/client` are OpenTUI's `input` and `textarea`,
made controlled: `value` in, and the text out through `onInput` on `<Input>` and `onChange` on
`<Textarea>`. A `name` makes their text restorable. On mount, that same prop receives the
restored text once. Pass the other prop, and your app's state stays empty and the field comes
back blank:

<Excerpt

  find="<Textarea"
  after='id="composer"'
  until="/>"
  mark={['name="chat/prompt"']}
  tone="client"
/>

A value your app sets from outside replaces the content and puts the cursor at the end.

## Keep the text of a field of your own

For a field of your own, such as an editor or a canvas, call
`useRestoredField(name, value, onChange)` to restore its text. When the field mounts, the kept
text comes back once through `onChange`. Pass each text the user types to the function it
returns. Notes keeps the Markdown of its WYSIWYG editor this way:

## Keep the focus and the scroll position

A browser gives the focus back to the field the user left, and scrolls the page back. A
terminal app decides its focus itself, with `focused={…}`, and scrolls boxes rather than a
page. So both are opt-in, by name:

- `useRestoredFocus(names)` returns `[focus, setFocus]`, your app's focus state, kept per entry.
  The focus starts on the first name until the user moves it. If the kept name is no longer in
  `names`, because the field was removed, the focus returns to the first name.
- `<ScrollBox name>` is OpenTUI's `scrollbox` with its position kept per entry. For a moment
  after mounting, the kept position waits for the content to be tall enough, such as a list the
  page loads or a live feed. If the user scrolls in the meantime, the user's scroll wins.

## Send a form without sending it twice

A group gathers the fields named `group/field`. `useRestoredFields("group").submit(action)`
forgets their text **before** the request leaves, on disk too. A Client killed while sending
does not offer the text again. `tests/restore-submit-kill.test.ts` kills one with SIGKILL as
its save leaves, then checks that the next Client starts without the text.

The text is kept again, unless the user typed something newer meanwhile, when:

- the outcome proves nothing ran (`not-sent`, `rejected`)
- `failed(result)` says the Server refused it

`clear()` forgets the text on demand.

## Use a form library

The framework neither validates nor sends forms. Use a library's hooks to drive a field by
value and callback. A terminal has no `<form>`, so a key binding submits the form.

| Library         | Use                                                      | Avoid                                     |
| --------------- | -------------------------------------------------------- | ----------------------------------------- |
| TanStack Form   | `useField`, and `form.handleSubmit()` from a key binding | `<form.Field>`                            |
| React Hook Form | `useController`                                          | Nothing                                   |
| Formik          | `useFormik` and `handleChange("field")`                  | `<Form>` and `<Field>`, which render HTML |

The examples follow TanStack Form, in Forge's new pull request form
(`components/NewPullForm.tsx`). TanStack's `<form.Field>` and `<form.Subscribe>` are headless
components, but their return signatures fail OpenTUI's JSX types.
[Upstream libraries](/docs/reference/upstream-libraries/#tanstack-form-hooks-with-terminal-callbacks)
shows the hook adaptation.

## Where is the text stored?

- Each Client has its own file, like a browser tab, with mode `0600`. The files are in
  `$XDG_STATE_HOME/luciole/<app>/sessions/`, which defaults to `~/.local/state/…`.
- The Client writes its file 200 ms after the last change, and before it exits on a signal. A
  send writes it at once.
- A `kill -9` cannot be caught. Text typed in the last 200 ms before one is lost.
- After a crash, the next Client takes over the newest restored session a dead Client left for
  the same [Server key](#which-client-gets-the-text-back). It never takes the file of a living
  Client.
- A file holds at most 50 history entries. A field longer than 100,000 characters is not kept.
- A file left by a dead Client is deleted after 7 days.
- A dead Client's process ID that the system gives to a new process makes its file look alive.
  The file is then neither taken over nor deleted.

A file holds the history and each entry's named fields. Here is one of Notes, in
`~/.local/state/luciole/notes/sessions/`:

```json
{
  "version": 1,
  "server": "local:/Users/ada/examples/notes",
  "pid": 48213,
  "updatedAt": 1790350000000,
  "index": 1,
  "entries": [
    { "href": "/", "fields": {} },
    { "href": "/notes/42", "fields": { "note/text": "A line not saved yet" } }
  ]
}
```

An entry with a kept focus or scroll position adds `"focus"` or `"scroll"`, such as Forge's
`"scroll": { "pull/timeline": 12 }`.

<Note kind="warning">
  The text of named fields is written to disk unencrypted. Leave a password or a PIN without a
  `name`, so that it is never written.
</Note>

<Note kind="warning">
  The restored session belongs to the system user, like a browser profile. After a crash, an account
  that signs in first sees the text the previous account typed.
</Note>
