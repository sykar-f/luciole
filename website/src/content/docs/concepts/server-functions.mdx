A module that starts with `"use server"` exports functions the Client can call. The build
registers them on the Server and replaces them, in the Client, with references. Calling a
reference sends `POST /action` with the arguments in Flight, and resolves with what the
function returned. There is no RPC layer, schema or manifest to write.

## What a `"use server"` module may export

- Exports are **named, async function declarations**. Inline functions, closures, exports
  by variable, default exports and re-exports are refused with the file and line.
- The one other runtime export allowed is `export const auth = "public" | "required"`,
  which applies to every function of the module ([authentication](/docs/concepts/authentication/)).
- Do not rely on `.bind`, or on passing a Server Function as an argument to another. Neither
  is part of the validated API.
- A Client Component may import the module directly, or receive a function as a prop from a
  page. Both go through the same call.

## Validate the arguments yourself

Arguments arrive decoded by Flight but **not verified**. A TypeScript type describes what
the Client is supposed to send, not what arrives. The framework only guarantees a list of
arguments. Validate them before any effect, as Notes does with Zod (`SnapshotInput.parse`
above).

When validation throws, the Server answers with a generic `500`. The caller then sees the
outcome `unknown`, [described below](#when-a-call-fails). No message, stack or path leaves
the Server.

## When a call fails

Every failed request throws a `TransportError` whose `outcome` says what the Server may have
done:

| `outcome`  | Cases                                                                                                                     | Did the Server call the function? |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| `not-sent` | Connection refused, host unreachable, aborted before sending                                                              | No                                |
| `rejected` | A `4xx`: no token (`AuthenticationRequired`), another build (`BuildMismatch`), unknown Server Function, bad argument list | No                                |
| `unknown`  | Timeout or cut after sending, response lost or truncated, a `5xx`                                                         | Maybe                             |

`rejected` means that the Server did not call the function. Some of your code may still have
run: the Server calls `authenticate` from `server/auth.ts` before it checks the build.

A thrown argument check is `unknown`, because the framework cannot tell what ran before the
throw. The transport reports `unknown` for every failure it does not recognise.

The transport **never retries** a call. `tests/http-transport.test.ts` checks that a failed
call sends one request, whatever its outcome. Your app decides what comes next:

- retry;
- look the operation up;
- mark it unknown;
- only show a message.

Notes looks an unknown save up first, by its operation ID. When the Server has no trace of
it, Notes sends the same operation again, and the Server applies it at most once:

`useApplication().withSignal(signal, () => action(...))` ties an abort signal to any Server

## Declare what a Server Function changed

The framework refreshes nothing by itself after a Server Function, so a read costs no page
render. A function that changes data calls `invalidate()` from `@luciole-sh/core/server`:

- the paths and tags travel back in the response's envelope (step 8 above);
- the Client revalidates the routes concerned (steps 11 and 12);
- the call resolves without waiting for those routes (step 13).

| Call                       | Effect                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `invalidate()`             | Revalidates every route (`"/"`).                                                                       |
| `invalidate("/repos/web")` | That path and its descendants, never a mere prefix (`/repos/website` is not included).                 |
| `invalidate({ tag })`      | Purges the Server cache for that tag, then the routes that read it ([caching](/docs/concepts/cache/)). |

A lost response invalidates nothing in the Client. Two hooks cover what route loaders do not
reload:

- `useInvalidation(listener)` runs after each invalidation, for data read outside route
  loaders, such as a counter in a layout. Notes reloads its sidebar's list this way
  (steps 9 and 10).
- `useApplication().invalidate(paths?)` lets Client code revalidate after a change it
  observed itself.

## Stream values from a Server Function

An `export async function*` in a `"use server"` module streams its values. `useLive` opens
the request when the component mounts, or when its arguments change. It cancels the request
on unmount, and the Server then stops the generator and runs its `finally`.

```tsx
const { items, done, error } = useLive(checkLog, [check.id], { limit: 500 });
```

Nothing reconnects by itself: a cut ends the stream with a `TransportError` (`unknown`). A
live response is exempt from the Server's idle timeout.

<Note>
  Each call carries a `callId` (`x-luciole-call`), which the Server reads with `getCallId()`: it
  links the Client's and the Server's events of one request, in the
  [DevTools](/docs/guides/devtools/) as in your logs. It identifies the request, not the business
  operation.
</Note>
