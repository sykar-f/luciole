# Q1 — should an uncaught exception end the Client?

Finding (audit point 1, checked in node_modules/@opentui/core): `createCliRenderer`
installs `process.on("uncaughtException" | "unhandledRejection", handleError)`; the handler only
`console.error`s and opens OpenTUI's on-screen console. It does NOT exit. Measured: a page that
throws from a timer after its first render leaves the Client alive, terminal still in the
alternate screen, console panel showing the error. OpenTUI's signal handlers (SIGINT, SIGTERM,
SIGHUP, SIGQUIT, SIGABRT...) destroy the renderer, but it registers no `exit` hook:
a bare `process.exit()` leaves the terminal raw.

So "terminal left raw after an exception" is refuted as stated (the process does not die),
but "terminal left raw after process.exit / any exit path" is real.

Options:
A. (recommended, minimal) Keep OpenTUI's swallow. Add in run.tsx a `process.on("exit")` that
   destroys the renderer (covers every process.exit path). Acceptance test 1 then proves: a
   Client with an exception after first render stays alive with the terminal valid, and a later
   exit writes the reset sequences (leave alternate screen, show cursor).
B. Also register uncaughtException/unhandledRejection in run.tsx: destroy the renderer, print
   the error to the restored terminal, exit(1). Matches the goal's wording ("an uncaught
   exception ends the process") but changes behaviour: any stray rejection in an app kills
   the Client instead of showing OpenTUI's console.

I proceed with A's common part (exit hook, PTY registry, shutdown hoist) now; B is a small add-on.

## Answer

A. The goal is that whatever ends the Client restores the terminal; it never asked that an exception end the Client. OpenTUI keeps the Client alive and shows the error in its console, which is the better behaviour for an app with a stray rejection; killing it would change behaviour users see. So: keep OpenTUI's handlers, add the `exit` hook (renderer destroy, PTY registry kill), and make acceptance test 1 prove both halves you describe (an exception after first render leaves the Client alive with a valid terminal; a later `process.exit` writes the reset sequences). Say in the delivery that audit point 1 was refuted as stated, with the OpenTUI file and line.
